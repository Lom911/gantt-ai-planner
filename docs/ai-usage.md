# Журнал использования AI-ассистентов

Журнал ведётся по ходу работы. Из него собирается раздел README «Как использовались AI-ассистенты». Записываются только факты: что делал инструмент, что решал человек, где AI ошибся.

Инструменты: **Claude Code** (модель Claude Opus 5.5; основной ассистент, оркестрация субагентов) и **Codex** (второе мнение и ревью).

## 2026-09-25 — Анализ ТЗ и проектирование

- **Чтение ТЗ.** Claude Code извлёк текст из PDF через MCP-сервер markitdown.
- **Проверка окружения.** Claude Code сам выяснил установленные инструменты, авторизацию в GitHub и Vercel, а также наличие браузеров Playwright для записи демо.
- **Опрос по дизайну (skill `grilling`).** Прошло 5 раундов вопросов. На каждый вопрос Claude давал рекомендацию, решение принимал человек. Человек изменил три рекомендации:
  - хостинг: свой VPS вместо Render;
  - БД: PostgreSQL вместо SQLite;
  - домен: DuckDNS.
- **Фоновые исследования (субагенты):**
  - сравнение React-библиотек для Гантта: лицензии, поддержка React 19, возможности бесплатных версий. Выбрана SVAR React Gantt (MIT), запасной вариант DHTMLX v10;
  - поиск в соседних проектах пользователя описания VPS и принятых соглашений (Caddy + DuckDNS);
  - лучшие практики хранения данных и секретов: Compose secrets, роли Postgres, CI без секретов приложения, 152-ФЗ.
- **Осмотр VPS.** Claude подключился по SSH только на чтение: проверил ресурсы, занятые порты, доступность API Anthropic из региона сервера.
- **Второе мнение (Codex).** Codex критически разобрал весь дизайн. Что учтено:
  - урезание объёма по фазам;
  - упрощение истории изменений;
  - внешний MCP перенесён во вторую фазу;
  - smoke-тест модели.

  Что отклонено и почему:
  - «чат без MCP» — тогда MCP стал бы декоративным, поэтому выбран MCP-клиент внутри процесса.
- **Спецификация.** Её написал Claude, при самопроверке он нашёл противоречие: колонка «Не раньше» была нужна, чтобы экспорт загружался обратно без потерь.

## 2026-09-25 — Реализация (subagent-driven development)

- **План.** Claude написал план из 23 задач. Для каждой задачи в нём есть файлы, интерфейсы, тесты и эталонный код. Факты об API библиотек (fastmcp 4, anthropic 1.8, sse-starlette) субагент сначала проверил пробными запусками в отдельном venv. Так выяснилось, что `mcp.server.fastmcp` в mcp 2.x больше нет, а по адресу `POST /mcp` без слэша приходит редирект 307.
- **Процесс.** Каждую задачу реализует новый субагент по TDD: красный тест, код, зелёный тест. Затем отдельный субагент-ревьюер проверяет соответствие брифу и качество кода. Найденные замечания исправляет тот же исполнитель, а результат снова проверяется.
- **Что поймало ревью.**
  - Исполнитель на дешёвой модели добавил в демо-план 3 лишние задачи, чтобы пройти тест. Это сломало бы контракт, на который опираются тесты следующих задач (25 задач, следующий id 26). Ревьюер это заметил, задачи вернули.
  - Ревьюер нашёл в плане ошибку на единицу в подсчёте переводов строк. Исполнитель исправил её осознанно и описал в отчёте.
- **Разногласие с атрибуцией.** Субагент отказался переписывать строку `Co-Authored-By` на модель оркестратора: у каждого субагента своя строка атрибуции, и она называет модель, которая на самом деле писала код. Решение принял оркестратор: в коммитах остаётся модель автора, а правило в плане исправлено.
- **Параллельная работа.** Чтобы уложиться в 3 часа, оркестратор запускал независимые задачи одновременно. Исполнители бэкенда, фронтенда, CI и деплоя работали в разных файлах. Правило было одно: в каждой области (бэкенд или фронтенд) в один момент работает только один исполнитель. Исправления по ревью передавались тому исполнителю, который уже работал в этой области.

  Однажды ревьюер сделал `git stash` в общей рабочей копии, и у соседнего исполнителя пропала правка. Её восстановили, а в промпты ревьюеров добавили явный запрет на команды, меняющие рабочую копию. Сборка Docker и e2e запускались в отдельном `git worktree`, чтобы незакоммиченная работа других агентов не попадала в образ.
- **Что ещё поймало ревью.**
  - Импорт падал с необработанным исключением, если лаг больше 365. Ошибку не заметил и план, но ревьюер воспроизвёл её на специально собранном файле.
  - Типы на фронтенде расходились с реальным API: `ImportSuccess`, `ApplyResponse.summary`.
  - Исполнитель неверно прочитал контракт `/api/events` и не подключил подсветку изменений из других источников.
  - Служебная метка фейковой LLM `[fake] shift=N` появлялась в тексте чата и попала бы в демо.
  - Модалка задачи могла молча откатить правку агента, если её не закрыли во время хода агента (устаревшая форма).
  - В Roadmap было упомянуто, что VPS используется и для других сервисов.
  - E2E-тест показал, что колонка с названиями задач в таблице SVAR схлопывается до нулевой ширины.
- **CI.** В GitHub Actions сразу выяснилось, что `gitleaks-action` v2 больше не работает на раннерах (Node 20 EOL). Исполнитель перешёл на v3.

## 2026-09-26 — Доработки перед деплоем

- **Порядок работы.** Человек решил сначала довести до конца всё, что можно сделать без сервера, и только потом разворачивать.
- **Второе мнение Codex по коду.** Codex нашёл три реальные проблемы, которые пропустили поштучные ревью:
  - **Гонка в лимите сообщений.** Лимит можно было обойти параллельными запросами: проверка и запись шли раздельно. Теперь это одна транзакция с advisory lock, и есть тест на конкурентность.
  - **Распаковочная бомба.** Лимит 2 МБ ограничивал только сжатый XLSX. Теперь размер после распаковки проверяется до openpyxl, а строки читаются лениво с ограничением.
  - **Тихий переход на фейковую LLM.** Без ключа Anthropic приложение незаметно работало на фейковой LLM. Отказаться от запуска Codex предлагал полностью. Человек и оркестратор выбрали другое: сайт продолжает работать, а в интерфейсе видна плашка «Демо-режим без LLM» (через `GET /api/meta`), в лог пишется ERROR.
- **Проверка по скриншотам.** Оркестратор сам смотрел скриншоты, которые исполнитель снимал через Playwright. Юнит-тесты при этом проходили, но на скриншотах было видно три проблемы:
  - критический путь не подсвечивался красным: CSS-селектор проигрывал SVAR по специфичности, а имя класса было неверным;
  - таблица занимала 620 px, и на саму диаграмму почти не оставалось места;
  - на мобильном снова схлопывалась колонка с названиями.

  Всё исправлено, результат перепроверен по новым скриншотам.
- **Совместимость с CSP.** Ревьюер кода заметил, что тема мигает при загрузке. Обычное исправление — inline-скрипт — сломалось бы на CSP продакшена (`default-src 'self'`), поэтому скрипт вынесен в отдельный файл `theme-init.js`.

## 2026-09-26 — Состязательное ревью Codex и `/code-review`

- **Два ревью подряд.** Ветка `phase-1-core` (205 файлов) прошла состязательное ревью Codex (`/codex:adversarial-review`, вопрос «правильный ли это подход») и обычное ревью Claude (`/code-review`). Codex нашёл три архитектурных пробела, Claude — девять дефектов реализации. Человек попросил исправить всё; каждое замечание сначала проверялось по коду, все двенадцать подтвердились.
- **Что нашёл Codex.**
  - **Нет оптимистичной блокировки.** Вторая вкладка могла молча затереть правку агента или другой вкладки. Теперь правки из интерфейса несут `expected_version`, сервер отвечает `409 version_conflict`, вкладка перезагружает план.
  - **Число связей не ограничено.** Задач не больше 500, а связей можно было накопить ~125 тысяч — по одной в каждом из 50 снимков версий. Введён лимит 2000 связей (операции, импорт, валидация плана). Рейт-лимит на мутации, который Codex предлагал дополнительно, не добавлен: с ограничением связей, задач и размера пакета стоимость одного запроса ограничена.
  - **Формулы в экспорте.** Задача с названием `=HYPERLINK(...)` уезжала в Excel живой формулой. Текстовые ячейки экспорта принудительно строковые, добавлен тест на round-trip.
- **Что нашёл Claude.** Бесконечный ре-рендер модалки задачи, если сервер меняет поле, которое пользователь как раз правит; `set_project_start` без сдвига задач не создавал версию; три параллельных `POST /api/session` при первой загрузке; удаление задачи падало, если сумма лагов мостика больше 365; разбор XLSX блокировал event loop; лишний `GET /api/plan` после каждой собственной правки; дублирование парсера ошибок; трёхкратный `schedule()` на каждый запрос; расхождение группировки исполнителей по регистру между планировщиком, MCP и панелью загрузки.
- **Случайная перезапись.** При добавлении тестов оркестратор командой `cat >` затёр существующий файл `taskOps.test.ts`; заметил по `git status` (файл значился `M`, а не `??`), восстановил из `HEAD` и дописал новые тесты.

## 2026-09-26 — Деплой и проверка на настоящей LLM

- **Ключ оказался ключом OpenRouter.** Ключ, который владелец выдал под `ANTHROPIC_API_KEY`, был не ключом Anthropic, а ключом OpenRouter (`sk-or-...`). Вместо смены на другой SDK Claude Code пробными запросами проверил Anthropic-совместимый эндпоинт OpenRouter и добавил провайдера `LLM_PROVIDER=openrouter` поверх того же `anthropic` SDK (`base_url` + `auth_token` вместо `x-api-key`, коммит `e159b83`). Заодно добавлено автораспознавание: ключ `sk-or-...` в `ANTHROPIC_API_KEY` при `LLM_PROVIDER=anthropic` тоже уходит через OpenRouter, с одноразовым предупреждением в логе.
- **Параллельная сессия.** Одновременно другая сессия Claude Code коммитила исправления по состязательному ревью Codex (`6f91db2`). Координация — сообщением между сессиями и коммитами, ограниченными по путям, чтобы не задеть файлы друг друга.
- **Классификатор auto-mode заблокировал удалённые правки на VPS**, пока человек явно не подтвердил доступ к серверу — сработало как задуманный барьер, а не как сбой.
- **Шаги деплоя.** Образ передан на сервер через `docker save | ssh` (без публикации в GHCR на этом шаге), выполнен `bootstrap.sh`, ключ OpenRouter записан в секрет через stdin, не печатаясь ни в лог, ни на экран.
- **Живой smoke-тест на проде** (модель — через OpenRouter, `anthropic/claude-sonnet-5`):
  - «Сдвинь все задачи Дмитрия на 3 дня» — сдвинуто ровно на 3 рабочих дня, конец проекта 17.11 → 20.11;
  - «Назначь аналитику на Ольгу» — по неполному имени однозначно определена Ольга Никитина;
  - добавление задачи с зависимостью и исполнителем — выполнено одним ходом;
  - «Перенеси задачу про API на 2 дня» — по названию подошло 4 задачи, агент переспросил, какую именно, вместо того чтобы угадывать;
  - массовое удаление — сервер потребовал `confirmation_required`, агент переспросил, удаление выполнено только после ответа «да».
- **Более ранний инцидент, не попавший в журнал вовремя.** Kaspersky на машине разработчика пометил как угрозу install-скрипт npm-пакета `ffmpeg-static` (использовался для конвертации записи демо в `scripts/record_demo.mjs`). Заменили на запуск ffmpeg внутри одноразового Docker-контейнера (`jrottenberg/ffmpeg`) — без npm-зависимости с install-скриптом, скачивающим бинарник.

## 2026-09-26 — CD и финальная проверка прода

- **Проверка документации по факту.** Субагент документации написал в README, что на окружении `production` включены required reviewers и что пакет GHCR «один раз сделан публичным». Оркестратор сверил это с GitHub API: на окружении только политика ветки `main`, а пакета тогда ещё не существовало. Обе фразы исправлены до мержа.
- **Первый прогон CD.** После мержа PR #1 в `main` CI и деплой отработали автоматически: образ собран, просканирован Trivy, опубликован в GHCR, сервер скачал его без логина — пакет публичного репозитория унаследовал публичную видимость, ручной шаг из рантбука не понадобился (рантбук поправлен).
- **Сквозная проверка прода в браузере.** Claude Code написал временный Playwright-сценарий против боевого домена с настоящей LLM: модалка задачи (правка длительности, история), отмена/повтор, импорт примера Excel, два хода агента (массовый сдвиг, добавление задачи с зависимостью), экспорт, выпуск MCP-токена, тема, сброс к демо. Сценарий дополнительно собирал ошибки консоли и ответы 4xx/5xx. Функционально всё прошло, но нашлась шероховатость: на первом заходе `/api/plan` и `/api/events` уходили до создания сессии, получали 401 и восстанавливались — браузер логировал это как ошибки консоли. Исправлено созданием сессии до первого рендера; в e2e добавлена проверка «ни одного 4xx/5xx на первом заходе» — сначала она упала на старом проде (красный тест), после исправления прошла в CI. Заодно `HEAD /` отвечал 405 — теперь 200.
- **Внешний MCP настоящим клиентом.** Скрипт на `fastmcp.Client` против прода: неверный токен отклоняется, все 6 инструментов доступны, правка через `apply_operations` сразу видна в API браузера, `undo` откатывает, отозванный токен перестаёт работать. Импорт битого файла даёт понятную ошибку, экспорт загружается обратно без потерь.
- **Ловушка Dependabot.** Бот предложил Postgres 17 → 18 (два PR, CI одного из них зелёный). Мажорная версия Postgres не запускается на каталоге данных предыдущей — такой мерж положил бы БД при следующем обновлении compose. PR закрыты с объяснением, в `dependabot.yml` добавлено правило, запрещающее мажорные обновления Postgres.
- **Мажорные обновления Dependabot.** Человек попросил влить все открытые PR бота (Node 26 в Dockerfile, TypeScript 7, vitest 5, jsdom 30, jest-dom 7, @types/node 26). Claude Code слил их ветки в одну интеграционную (один прогон CI и один деплой вместо шести, без конфликтов `package-lock.json`); исходные коммиты бота вошли в `main`, поэтому GitHub сам пометил PR как влитые. PR с jsdom 30 падал в CI: все воркеры vitest завершались с `webidl.util.markAsUncloneable is not a function`. Причина — не jsdom, а Node: jsdom 30 (через undici 8) и vitest 5 требуют Node ≥ 22, а CI работал на Node 20 (EOL). CI переведён на Node 26 — ту же версию, что в сборочной стадии Dockerfile; перед пушем всё проверено в контейнере `node:26-alpine` (lint, typecheck, 80/80 тестов, сборка), после деплоя повторены проверки прода: CSP, мобильная раскладка, внешний MCP, чат на настоящей LLM.
- **Скриншот от человека вместо тестов.** После всех зелёных проверок человек прислал скриншот прода: диаграмма открывалась прокрученной к «сегодня», у первых задач плана не было видно полос, подписи были обрезаны у левого края. Автотесты этого не ловили — они проверяли, что полосы есть, а не что их видно. Исправлено: диаграмма открывается с начала проекта (линия «сегодня» по спецификации всё равно попадает на первый экран на десктопе). Заодно по замерам DOM найдены и исправлены обрезанные заголовки «№»/«Дн.» (пустой слот сортировки SVAR резервировал 15 px) и потерянные 30 px в колонке названий (заглушка под значок дерева, которого у плоского плана нет).
- **Баг, найденный собственным лимитом.** Во время визуальных проверок Claude Code исчерпал лимит 20 новых сессий в час с одного IP — и обнаружил, что в этом случае страница навсегда зависает на «Загрузка плана…», отправляя ~4 запроса в секунду: запрос плана повторял ответ 429, а переподключение потока событий каждые 2 с сбрасывало запрос заново, скрывая ошибку. Теперь ошибки 4xx не повторяются (пользователь сразу видит «Слишком много новых сессий… Попробуйте через час»), поток событий переподключается с экспоненциальной паузой до минуты. Для проверки вёрстки без расхода сессий сделан прогон локальной сборки на замоканном API с демо-планом, сгенерированным кодом бэкенда.
- **Нет полосы прокрутки.** Следующий скриншот человека: «внизу нет бегунка, чтобы двигать график». Замер DOM показал причину глубже симптома: обёртки SVAR (тема и область подсказок) были блоками с высотой `auto`, поэтому диаграмма вырастала на всю высоту всех строк, а панель раскладки её обрезала — горизонтальная полоса прокрутки оказывалась ниже видимой области, а задачи 20–25 были недостижимы вообще (вертикальной прокрутки тоже не было). Ни один тест этого не ловил: Playwright в headless-режиме прячет полосы прокрутки, а тесты проверяли наличие полос задач, а не их достижимость. Добавлен e2e-тест «диаграмма помещается в панель, последняя задача достижима прокруткой» — сначала красный на старом проде, потом зелёный.
- **«Откуда отсчёт?»** Вопрос человека показал, что на экране нигде не видно даты старта проекта. Сначала Claude Code взял готовые маркеры SVAR с подписями, но они не появились: разбор бандла показал, что MIT-сборка хранилища принудительно обнуляет `markers` (функция PRO). Вместо них — своя зелёная линия по столбцу даты старта и даты «Старт · Окончание» в легенде. По ходу выяснилось, что подсветка столбца «сегодня» в теле диаграммы никогда не работала (SVAR позиционирует такие столбцы только через свой класс `.wx-weekend`, наши схлопывались в ноль) — исправлено, добавлен e2e-тест.

## 2026-09-26 — аудит безопасности перед сдачей

- **Что сделано.** По просьбе «проверь код на уязвимости, свежесть библиотек и явные дыры» Claude Code провёл аналог пред-продового пентеста: SCA (`npm audit`, `pip-audit`, gitleaks по всей истории — всё по нулям), SAST (bandit, semgrep с 297 правилами — по нулям), три параллельных ручных аудита субагентами (backend, frontend+CI, deploy) и DAST — поднял стек в Docker с фейковой LLM и прощупал: CSRF по Origin, флаги cookie, жизненный цикл MCP-токена (чужой/отозванный/после удаления сессии), лимит загрузки, xlsx-бомбу, лимит операций, формульную инъекцию в экспорте, 50 параллельных SSE, утечку трассировок, path traversal. Всё это выдержало.
- **Главная находка — ReDoS в импорте Excel.** Субагент backend-аудита заметил, что колонка «Предшественники» единственная не обрезается по длине, а две регулярки разбора (`_NUM_REF_RE`, `_NAME_LAG_RE`) квадратичны на строке из пробелов. Оркестратор не поверил на слово и замерил сам в venv проекта: 20 000 пробелов — 10 секунд на одну ячейку, рост ×4 при удвоении длины. Такая ячейка сжимается в килобайт, проходит лимит 2 МБ и защиту от zip-бомбы, а `re` держит GIL при единственном worker'е — один файл кладёт всё приложение в restart-loop. Сканеры (bandit, semgrep) этого не увидели — нашёл только чтец кода.
- **Второе по важности — deploy.** Тег образа `sha-xxxxxxx` мутабельный, а сервис миграций запускается без hardening и с правами владельца БД; общая docker-сеть `edge` позволяет соседнему контейнеру на VPS ходить в приложение мимо Caddy. Остальное — Medium/Low: бюджет токенов LLM на ход, рост БД без верхней границы, `mask_error_details` в fastmcp, IPv6 /64 для лимитов.

## 2026-09-28 — задачи из интерфейса и мелкие правки диаграммы

- **Что просил человек** (по ходу одной сессии, по скриншотам): число дней в подписи «Старт · Окончание»; выделение столбца по клику на дату, как у «сегодня»; поменять местами иконки «Загрузить Excel» и «Экспорт»; одинарный клик по строке — выделение, двойной — карточка, плюс карандаш в конце строки; кнопки «добавить задачу» и «удалить задачу», вставка задачи между двумя, и чтобы агент умел то же.
- **Что сделано.** Подпись показывает календарные дни включительно («(80 дней)»). Клик по числу в шкале дней красит столбец (синий, чтобы не путать с фиолетовым «сегодня»); дата вычисляется из ячеек шкалы SVAR (`_scales`), у которых в DOM нет атрибута с датой, — в типах SVAR `date`/`unit` ячейки не объявлены, хотя есть во время выполнения. Двойной клик ловит свой контейнер, а `show-editor` SVAR только блокируется: иначе, пока агент занят (диаграмма read-only), карточка не открывалась бы вовсе. Новая задача — форма с «Начать после», «Перед задачей» и местом в списке; если выбранные задачи были связаны, одним пакетом `add_task` + `remove_dependency` + `add_dependency` (id новой задачи = `last_id + 1`, пакет идёт с версией плана). Удаление — из карточки с подтверждением; связи через задачу бэкенд уже сохранял (A→B→C → A→C). Агенту в промпт и в описания полей схемы добавлены правила вставки «между A и B» и удаления; живая проверка на локальном стеке с OpenRouter — «Вставь задачу «Ревью макетов» на 2 дня между 6 и 12» дала ровно 6 → новая → 12 и новую строку сразу после 6.
- **Проверка.** vitest 118/118, интеграционные тесты бэкенда 176/176; e2e против локального стека: выделение дня, клик/двойной клик/карандаш, вставка-добавление-удаление (`task-crud.spec.ts`); сценарии с чатом на настоящей LLM не запускались ради экономии ключа. Параллельно в том же репозитории работала вторая сессия (сворачиваемый чат): её файлы не трогались, одна сборка Docker упала на её незаконченном тесте и прошла после того, как она дописала реализацию.
- **Второе мнение Codex и исправления.** Codex (read-only ревью незакоммиченного диффа) нашёл: на телефоне колонка с карандашом раздвинула таблицу до 216 px при проверке «не шире 185 px» — колонки сужены (№ 36, «Задача» 116, карандаш 32; первая попытка дала 186 px из-за рамки таблицы, её поймал e2e); выделение дня было только мышью — ячейки шкалы стали кнопками с одной точкой табуляции, ←/→ и Enter/пробел (SVAR перерисовывает виртуальную шкалу, поэтому атрибуты переустанавливает MutationObserver); подтверждение удаления переживало закрытие карточки; ширина таблицы, сохранённая до появления карандаша, прятала его — такая ширина один раз расширяется на колонку (`gridIncludesEdit`); вставка, замыкающая цикл, теперь отклоняется в форме с номерами задач, а не общей ошибкой сервера; в схеме и промпте описано, что при удалении лаги двух связей складываются (до 365). Замечание про иконки импорта/экспорта не принято: их направление выбрал человек. По ходу найдена чужая утечка мока в `layoutPrefs.test.ts` (подменённый `setItem` не восстанавливался, и последующие сохранения в тестах молча не срабатывали) — добавлен `afterEach(vi.restoreAllMocks)`. Полный `npm run e2e` на локальном стеке с fake-LLM (как в CI) — 19/19, включая полный прогон интерфейса 67/67 и граничные случаи 36/36.

## 2026-09-28 — выделение после перетаскивания и «залипшая» подсказка

- **Жалоба:** после растяжения полосы «Корзина и оформление заказа» дни менялись, а выделенной оставалась прежняя строка; подсказка над полосой показывала дни до изменения.
- **Причина:** SVAR подавляет клик, которым браузер завершает перетаскивание (флаг в обработчике окончания drag), — а выделение ставилось только по клику. Подсказка SVAR берёт снимок задачи при появлении и держит его, пока указатель не сдвинется; во время перетаскивания она висела на месте нажатия со старыми датами. Найдено чтением собранного кода SVAR и воспроизведено скриптом Playwright; Codex вторым мнением подтвердил и добавил случай «потянули и вернули на место» (SVAR тогда шлёт `drag-task` без `update-task`).
- **Исправление:** задача выделяется по `update-task` с `diff` и по `drag-task` с `inProgress: false`; подсказка читает задачу из плана (обновляется, как только ответил сервер) и скрыта, пока полоса зажата. Новый e2e-тест в `layout.spec.ts`; заодно убрана гонка в `edge.spec.ts` (импорт сразу после хода чата получал 409 «План только что изменился» — тест теперь, как пользователь, нажимает «Загрузить» ещё раз).

## 2026-09-28 — длина полосы и рабочие дни

- **Жалоба:** «Push-уведомления 01.10–07.10 · 5 раб.дн.», а полоса занимает 7 клеток — «длина не соответствует количеству дней».
- **Разбор:** расчёт верный — длительность в рабочих днях (Пн–Пт, `backend/app/domain/calendar.py`), полоса рисуется по календарным датам и перекрывает выходные. Но на диаграмме выходные ничем не отличались, и расхождение выглядело ошибкой. Codex вторым мнением сравнил варианты: скрыть выходные со шкалы в MIT-версии SVAR можно только своей единицей шкалы (`registerScaleUnit`), это ломает перетаскивание и расчёт длительности в `interactions.ts`; рекомендовал затенение и явную подпись.
- **Исправление:** субботы и воскресенья затенены в дневном масштабе (шкала и тело диаграммы, светлая и тёмная темы), в легенде — «Выходные» с пояснением; подсказка пишет «7 дней, из них 5 рабочих» (или «3 рабочих дня», если выходных внутри нет). Юнит-тесты `highlightDay`/`durationLabel`, e2e в `layout.spec.ts`.

## 2026-09-28 — после деплоя браузер показывал старый интерфейс

- **Симптом:** пользователь прислал скриншот со старой подсказкой («6 раб.дн.»), хотя на проде уже была новая («8 дней, из них 6 рабочих») и затенённые выходные.
- **Причина:** `index.html` отдавался без `Cache-Control` — браузер кэшировал его эвристически (часть времени с `Last-Modified`) и после деплоя продолжал грузить прошлую сборку. Codex вторым мнением согласился и уточнил: `immutable` ставить только файлам, которые реально отданы и имеют хэш в имени (отсутствующий `/assets/…` уходит в SPA-fallback и отдаёт `index.html`); проверено, что `FileResponse` не отвечает 304, — `index.html` ~1 КБ, это приемлемо.
- **Исправление:** `backend/app/main.py` — всё `no-cache`, кроме хэшированных файлов из `assets/` (`public, max-age=31536000, immutable`); тесты в `test_spa_fallback.py`. Заодно выходные сделаны чуть тусклее по просьбе пользователя.

## 2026-09-28 — keep-alive между Caddy и uvicorn

- **Как нашлось:** локальный e2e дважды упал с `socket hang up` на обычном запросе к API. Гипотеза — uvicorn закрывает простаивающее keep-alive соединение через 5 с (дефолт), а клиент в этот момент его переиспользует. Воспроизведено скриптом на `http.client`: GET, пауза 6 с, POST на том же сокете → `RemoteDisconnected`; с паузой 3 с — нормальный ответ.
- **Риск для прода** (Codex вторым мнением, со ссылками на документацию Caddy и исходники Go): Caddy держит простаивающие соединения к приложению 2 минуты и переиспользует их; POST с телом Go-транспорт повторить не может — пользователь получил бы 502 на правке плана или сообщении в чат, редко и без следа в логах приложения.
- **Исправление:** `--timeout-keep-alive 180` в `Dockerfile` (больше двух минут Caddy). После пересборки тот же скрипт проходит с паузой 6 и 20 с, два полных e2e-прогона подряд без обрывов. Настройку Caddy не меняли: серверный Caddyfile ставится вручную, а фикса на стороне приложения достаточно.

## 2026-09-29 — чат с чистого листа, «История» и «Сегодня»
