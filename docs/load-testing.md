# Нагрузочное тестирование

Базовый профиль нагрузки для текущей конфигурации (один воркер uvicorn, контейнер приложения 300 МБ). Скрипт — `scripts/loadtest.py`.

## Методика

Виртуальный пользователь в цикле: создаёт сессию → открывает поток событий (`/api/events`) → читает план → 5 правок (`/api/plan/operations`) → отмена → один ход чата (фейковая LLM) → экспорт Excel → удаляет сессию. Ступени по 30 с: 5, 10, 25 одновременных пользователей.

Стенд — одноразовый, изолированный, **на самом прод-VPS** (2 vCPU, 1,9 ГБ RAM; сервис делит машину с другими): тот же образ, отдельная временная БД, отдельная internal-сеть, наружу не открыт, фейковая LLM, лимиты на IP подняты (вся нагрузка идёт с одного адреса). Приложению выделено 1 CPU и 300 МБ — как в проде; после теста стенд удалён. Локальный прогон на Windows/Docker Desktop не показателен: там основное время уходит на сетевую прослойку Docker до БД.

```bash
# на машине с доступом к стенду (сеть lt-net), см. историю в docs/ai-usage.md
python scripts/loadtest.py --base-url http://lt-app:8000 --origin http://lt-app:8000 --stages 5,10,25 --seconds 30
```

## Результаты (p50, мс; ошибок — 0 во всех прогонах)

| Запрос | 5 польз. до | 5 польз. после | 25 польз. до | 25 польз. после |
|---|---:|---:|---:|---:|
| `GET /api/plan` | 212 | 127 | 651 | 678 |
| `POST /api/plan/operations` | 195 | 181 | 898 | 813 |
| `POST /api/chat` (фейковая LLM) | 647 | 570 | 3013 | 2792 |
| Пропускная способность, запросов/с | 20 | 22 | 22 | 24 |
| Пик памяти приложения | 146 МБ | 245 МБ* | | |

\* До уменьшения кэша планов до 2 МБ JSON (как Python-объекты план занимает ~10× свой JSON); текущая версия держит ~200 демо-планов в кэше.

«После» — оптимизации чтения: `last_seen_at` обновляется не чаще раза в 10 минут, текущая версия читается одним запросом, рассчитанный план кэшируется по неизменяемому `id` строки версии.

## Выводы

- **Узкое место — процессор одного воркера** (~45 мс CPU на запрос на vCPU этого VPS: FastAPI/Pydantic/SQLAlchemy, пересчёт расписания при правке). Память и БД запаса имеют.
- **Ёмкость:** ~20–24 запроса/с. Для демо и десятков одновременно работающих людей достаточно; живой чат упирается не в сервер, а в скорость LLM (ход 5–40 с).
- **Следующий шаг при росте** — несколько воркеров. Изменения плана уже сериализуются в БД (advisory lock), но шина событий SSE, блокировка «агент работает» и лимиты на IP живут в памяти процесса — их нужно перенести в Postgres (`LISTEN/NOTIFY`, advisory locks) или Redis (Roadmap).
