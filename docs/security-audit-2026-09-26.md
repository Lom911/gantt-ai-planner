## Динамические пробы (локальный стек, `LLM_PROVIDER=fake`)

Подтверждено: cookie `HttpOnly; SameSite=Lax` (в проде `__Host-` + `Secure`); чужой `Origin` на unsafe-запросах → 403; без сессии → 401; `/mcp` без токена, с чужим, после отзыва, после удаления сессии → 401; чужой `Origin` на `/mcp` → 403; файл > 2 МБ → 413; xlsx-бомба (1.5 МБ → 21 МБ) → 422 «слишком большой после распаковки»; > 200 операций → 422; формулы (`=HYPERLINK`, `+cmd|…`, `@SUM`) в экспорте сохраняются как текст, не как формула; 50 параллельных SSE-подписок не влияют на `/healthz`; ошибки без трассировок; path traversal → SPA fallback; `Content-Disposition` строится из распарсенной даты.

## Находки

### HIGH

**H1. ReDoS в импорте Excel — остановка приложения одним файлом.**
`backend/app/excel/parse.py:50-51` — регулярки `_NUM_REF_RE` (два смежных `\s*`) и `_NAME_LAG_RE` (`(.*?)\s*`) квадратичны; колонка «Предшественники» (`:229`) — единственное текстовое поле без обрезки по `LIMITS`. Ячейка из «1» + N пробелов + «x» сжимается в ~1 КБ, проходит лимит 2 МБ и защиту от zip-бомбы.
Воспроизведено: 5 000 пробелов — 0,7 с; 10 000 — 2,4 с; 20 000 — 10 с; O(n²), 1 МБ ячейка ≈ часы. `re` держит GIL, worker один → встают все сессии, `/healthz` падает, Docker перезапускает контейнер, атакующий повторяет. На `/api/plan/import` нет per-IP лимита.
Фикс: обрезать `preds` (например 500 символов) и каждый токен (64) до регулярок; `\s*(?:fs|он)?\s*` → `\s*(?:(?:fs|он)\s*)?`; `_NAME_LAG_RE` заменить на `token.rpartition("+")`; per-IP лимит на import.

**H2. Мутабельные теги образа + `migrate` без hardening (deploy).**
`deploy/compose.prod.yml:61-83` — `migrate` без `read_only`, `cap_drop`, `no-new-privileges`, `user:`; `IMAGE_TAG` вида `sha-xxxxxxx` можно перезалить в GHCR. Кто угодно с `packages: write` (или через push в `main`, required reviewers не включены) подменяет образ, и он запускается с паролем `planner_owner` (DDL).
Фикс: деплой по digest (`tag@sha256:…`, проверка в wrapper), `user: "10001:10001"` и тот же hardening для `migrate`, required reviewers на environment `production`.

### MEDIUM

**M1. Неограниченный контекст LLM внутри хода — расход API-ключа.** `backend/app/agent/loop.py:33,222-242` — 15 итераций, полный текст каждого tool_result в контекст, учёта `usage` нет. 500 задач × `get_plan` 14 раз ≈ 3M входных токенов ≈ $9 за ход; с лимитами 500/день ≈ до $4–5k/день. Фикс: бюджет токенов на ход (~150k), усечение tool_result, `max_iterations` 6–8.

**M2. Рост БД без ограничений.** `domain/models.py:5-17`, `plan_service.py:399-415` — снимок 500 задач × 2000 символов × 50 версий, нет per-IP лимита на `/api/plan/operations` и `/import` → десятки ГБ/сутки с одного IP; `task history` тянет все дифы в память (`mem_limit 300m`). Фикс: лимит байт снимка, per-IP лимит на operations/import, алерт на том.

**M3. Общая docker-сеть `edge`.** `compose.prod.yml:97-125` — любой контейнер соседнего сервиса достаёт `planner-app:8000` напрямую, минуя Caddy (лимит тела, заголовки, TLS) и подделывая `X-Forwarded-For` при `TRUST_PROXY=true`. Фикс: отдельная internal-сеть Caddy↔app.

**M4. `bootstrap.sh:105-106` перезаписывает общий `/opt/caddy/Caddyfile`.** Повторный запуск снесёт чужие сайты на VPS. Фикс: создавать только при отсутствии, либо `import /etc/caddy/sites/*.caddy`.

**M5. Бэкапы: тихий отказ cron, нет снимка перед автоматической миграцией, без шифрования/offsite.** `bootstrap.sh:160`, `planner-deploy:112`, `backup.sh:15`.

**M6. Hardening контейнеров неполный.** `db` без `cap_drop`/`no-new-privileges`; нигде нет `pids_limit`; tmpfs без `size=`.

## Второе мнение: adversarial-ревью архитектуры (Opus, вместо недоступного Codex)

Задача — оспорить решения, а не искать баги. Ниже только то, чего нет выше, с проверкой оркестратором ключевых тезисов.

**Подтверждено оркестратором:**

- **Глобальный дневной лимит чата обходится.** `services/ratelimit.py:16` считает строки `chat_messages` за сутки; `db/models.py:60` — `ondelete="CASCADE"` от сессии. Цикл «POST /api/session → 30 сообщений → DELETE /api/session» держит счётчик у нуля. Реально работает только in-memory лимит 60/час/IP. Обещание «500/сутки на всё приложение» из roadmap неверно. Фикс: append-only леджер квоты, не привязанный к сессии.
- **Тот же лимит — выключатель сервиса:** ~9 IPv4-адресов × 60/час выбирают 500 за минуты, дальше все пользователи почти сутки получают «Дневной лимит исчерпан». Фикс: резерв квоты для новых сессий, лимит в токенах по `usage` (в коде `usage` не читается нигде).
- **MCP-активность не продлевает сессию:** `mcp_server/auth.py:33-38` обновляет только `last_used_at` токена, не `sessions.last_seen_at` → пользователь только через Claude Desktop теряет план через 14 дней.
- **Текст предупреждения неточен:** `ChatPanel.tsx:92` «отправляется в LLM Anthropic», прод ходит через OpenRouter (`compose.prod.yml:93-94`) — второй получатель данных не назван.

**Аргументы по дизайну (не баги, решения):**

- Нет ротации токена сессии и абсолютного срока жизни; «выйти» = «удалить данные»; на общем ПК следующий человек видит план и чат и может перевыпустить MCP-токен, молча отозвав токен владельца. Нет `GET /api/mcp-token` со статусом/`last_used_at`. Токен выдаётся в готовой shell-команде (попадает в историю оболочки) и в JSON для конфига на диске.
- CSRF: Origin + `__Host-` + Lax — достаточно; правило «нет Origin → пропустить» закрывает Lax. Дешёвое усиление — отвергать `Sec-Fetch-Site: cross-site`. `McpOriginGate` на bearer-эндпоинте почти ничего не защищает, но отсекает браузерные MCP-клиенты.
- Session_id агента едет через contextvar поверх приватного `mcp/shared/_context_streams.py`; регрессия в транзитивной зависимости может дать запись в чужой план. Тест изоляции есть и поймает. Лучше явный `session_id` в общем слое инструментов.
- План кладётся в system prompt как доверенный текст; `confirmed` для массового удаления управляет сама модель. Ущерб — только своя сессия, откат `undo`.
- Второй воркер uvicorn: undo и apply гонятся (нет `FOR UPDATE`/advisory lock по сессии, `plan_service.py:372-415`), locks/EventBus/лимитеры локальны для процесса. Единственный worker — условие корректности, а не только масштаб.
- Автооткат деплоя не работает после миграции: старый образ упадёт на `alembic upgrade head` с неизвестной ревизией, сайт лежит. У `planner_owner` нет `lock_timeout`.
- Данные: дампы держат удалённое ещё ~8 дней; нет privacy-заметки; IP и usage не логируются вовсе — при скачке счёта расследовать нечего.

**Вердикт агента:** для демо выпускать как есть при условии жёсткого лимита расходов на ключе провайдера (OpenRouter, не Anthropic-workspace, как пишет roadmap). До реальных пользователей: леджер квоты, бюджет в токенах, обрезка tool_result, отдельная сеть Caddy↔app, деплой по digest, `SELECT … FOR UPDATE` по сессии.

**Оставлено сознательно:**

- **Required reviewers на environment `production`** — не включены, чтобы мерж в `main` сразу выкатывался. Подмену образа закрывают деплой по digest и проверка в wrapper.
- **Ротация токена сессии и абсолютный срок жизни.** Сессия анонимная, и её токен — единственный ключ к данным: ротация по сроку удалит план активного пользователя, а ротация на каждом запросе создаёт гонки между вкладками. Для общего ПК есть «Удалить мои данные».
- **Явный `session_id` вместо contextvar поверх приватного модуля MCP SDK.** Изоляцию сессий проверяет отдельный тест, который упадёт при регрессии в зависимости; переписывать слой инструментов ради этого риска не стали.
