# Roadmap to production

Что нужно доработать, чтобы довести Gantt AI Planner от публичного демо до сервиса с реальными пользователями и данными. Документ состоит из шести частей: что уже сделано для эксплуатации, осознанный технический долг, известные дефекты, чего не хватает для продакшена, риски и порядок закрытия. Детали реализации — в `README.md`, полная спецификация — в `docs/superpowers/specs/2026-09-25-gantt-ai-planner-design.md`, эксплуатация — в `docs/runbook.md`.

Состояние проверено 28.09.2026: демо работает на https://gantt-ai-planner.duckdns.org (один VPS, Docker Compose, Caddy, PostgreSQL), агент — на живой модели через OpenRouter (`anthropic/claude-sonnet-5`, `GET /api/meta`).

## Что уже сделано для эксплуатации

Чтобы не искать это среди «не хватает»:

- **Выкатка.** Автоматический деплой — только после зелёного CI (ручной запуск этого не проверяет, см. «Известные дефекты»): тесты backend/frontend, e2e на полном стеке, короткий нагрузочный прогон (порог ошибок 1 %), проверка, что предыдущий образ работает на схеме после новых миграций, Trivy и аудит зависимостей. Деплой только по digest образа, с блокировкой от параллельных выкаток, дампом БД перед обновлением и откатом образа без повторных миграций.
- **Данные.** Ночной `pg_dump` (7 дней), дамп перед каждым деплоем, зашифрованная копия в приватном репозитории бэкапов (30 последних) с еженедельной проверкой восстановления во временный Postgres. Удалённая копия включается отдельной настройкой сервера (runbook §4); на проде настроена, отправка и проверка восстановления прошли 27.09.2026.
- **Защита от злоупотреблений и расходов.** Лимиты на новые сессии, чат и импорт (в Postgres, переживают перезапуск), на правки плана и `/mcp` (в памяти процесса), дневная квота чата с резервом для адресов, отправивших за сутки меньше 10 сообщений. Бюджет хода агента: не больше 8 итераций и около 300 000 токенов — размер запроса оценивается до каждого вызова LLM, поэтому последний ответ может немного выйти за бюджет; ответы инструментов обрезаются.
- **Безопасность правок.** Массовое удаление подтверждается только человеком: в чате — точным «да» или «подтверждаю» следующим сообщением, для внешнего MCP-клиента — кнопкой в браузере; подтверждение привязано к конкретному пакету и версии плана. Правки одной сессии сериализуются блокировкой в Postgres, правки из интерфейса, импорт и внешний MCP передают ожидаемую версию и получают 409 вместо тихой перезаписи.
- **Наблюдаемость.** Каждые 15 минут: доступность, доля ошибок 5xx, p95, расход токенов за сутки, место на диске, свежесть бэкапа — при нарушении порога открывается issue. Еженедельный прогон шести эталонных диалогов на живой модели. Одна строка трассировки на ход агента (без текста сообщений).
- **Периметр.** Приложение и миграции — без root, `read_only`, `cap_drop: ALL`; Caddy — `read_only` и минимальные capabilities; Postgres — `cap_drop: ALL` с пятью capabilities, нужными его entrypoint; у всех лимиты памяти и процессов, `no-new-privileges`; приложение доступно только из Caddy по внутренней сети; cookie `__Host-`, проверка `Origin` и `Sec-Fetch-Site`, CSP.

## Осознанный технический долг

Упрощения, принятые ради объёма тестового задания. Это выбор, а не ошибки: каждое работает на масштабе демо и имеет понятный путь замены.

| Упрощение | Почему принято | Чем заменить |
|---|---|---|
| Один воркер uvicorn: шина событий SSE, флаг «агент работает» и часть лимитов живут в памяти процесса | На масштабе демо хватает одного процесса (20–24 запроса/с на одном выделенном CPU, чат — на фейковой модели, `docs/load-testing.md`); целостность плана уже обеспечена блокировкой в Postgres | `LISTEN/NOTIFY` или очередь для событий, флаг и лимиты — в Postgres или Redis; затем несколько воркеров и инстансов |
| План хранится целиком как JSONB-снимок на версию (до 500 задач, 50 версий) | Отмена и повтор — переключение указателя на версию; валидация и расчёт — над одним объектом | Нормализованные таблицы `tasks`/`dependencies`, когда вырастет лимит или понадобятся выборки по задачам |
| Анонимные сессии по cookie, без учётных записей и общих планов | Формат публичного демо: открыл страницу — работаешь | Учётные записи, владение планом, приглашения и права (просмотр/редактирование) |
| Календарь пн–пт без праздников | Праздники зависят от страны и требуют источника данных | Производственный календарь (например, `workalendar` с календарём РФ) в `backend/app/domain/calendar.py`, показ праздников на диаграмме |
| Только связи «конец → начало», задержка ≥ 0, без вех, один исполнитель на задачу | Покрывает основной сценарий; каждое расширение затрагивает планировщик, Excel, диаграмму и агента | SS/FF/SF и отрицательная задержка в CPM, вехи как отдельный тип задачи, список исполнителей |
| Внешний MCP — статический Bearer-токен (7 дней, один на сессию) | Достаточно для одного пользователя на сессию | OAuth 2.1 (authorization code + PKCE) вместе с учётными записями |
| Бэкапы в приватном GitHub-репозитории | Бесплатно, с шифрованием и проверкой восстановления | S3-совместимое хранилище с object lock: сейчас скомпрометированный сервер может удалить копии (ключ на запись) |
| Мониторинг через cron в GitHub Actions: окно 15 минут, без истории метрик | Без отдельной инфраструктуры покрывает «лежит / деградирует / дорого» | Prometheus/Grafana или облачный APM, трассировка вызовов LLM (OpenTelemetry) |
| VPS общий с другими сервисами: Docker не rootless, required reviewers не включены | Перевод демона затронул бы соседние сервисы; required reviewers отключили бы автодеплой | Отдельный хост или managed-платформа, ревью перед продакшен-выкаткой |
| CSP разрешает `style-src 'unsafe-inline'` | Инлайн-стили нужны SVAR Gantt и Tailwind | nonce/hash для стилей или замена компонентов с инлайн-стилями |

## Известные дефекты

Найдены аудитами (в том числе вторым мнением Codex), подтверждены по коду, пока не исправлены.

| Приоритет | Дефект | Сценарий |
|---|---|---|
| P1 | Карточка задачи может молча перезаписать чужую правку поля, которое пользователь уже редактирует (`frontend/src/components/task/taskOps.ts`) | Пользователь меняет длительность в открытой карточке, тем временем агент или другая вкладка меняет её же; при сохранении версия берётся из уже обновлённого кэша, поэтому 409 не срабатывает и чужое значение теряется. Изменения полей, которые пользователь не трогал, форма уже подхватывает |
| P1 | Удаление задачи с большим числом связей надолго занимает сервер (`backend/app/domain/operations.py`, «мост» A→C) | Удаление строит все пары «входящая × исходящая», O(in × out), а лимит в 2000 связей проверяется только после этого — у задачи с сотнями связей один запрос нагружает единственный воркер |
| P1 | Сбой отправки удалённой копии бэкапа не попадает в основной мониторинг (`backend/app/services/ops.py`) | Локальный дамп проходит, отправка в репозиторий бэкапов ломается — основной алерт молчит, сбой заметит только еженедельная проверка (она ругается на копию старше трёх дней) |
| P2 | При удалении промежуточной задачи сумма задержек обрезается до 365 дней — намеренно, чтобы не превысить предел модели, но без предупреждения | Две связи с задержкой по 365 дней становятся одной на 365 — последователь сдвигается раньше |
| P1 | Ручной запуск деплоя (`workflow_dispatch`) не проверяет, что CI для этого коммита зелёный | Оператор выкатывает `main` сразу после проваленного CI |
| P2 | Форма новой задачи не замечает, что выбранную «опорную» задачу удалили в другой вкладке, и не предупреждает о лимите 500 задач заранее | Сервер отклоняет пакет с ошибкой уже после заполнения формы |

## Чего не хватает для продакшена

- **Пользователи и права.** Регистрация и вход, владение планами, совместная работа (несколько людей на одном плане с живыми обновлениями), аудит действий. От этого зависит OAuth для MCP и юридическая сторона хранения данных.
- **Масштабирование.** Несколько воркеров и инстансов (см. техдолг), вынос состояния из памяти процесса, целевой SLO и регулярный нагрузочный прогон на реалистичном профиле, включая долгие SSE-соединения.
- **Данные и соответствие.** До приёма персональных данных — определить с юристом, какие требования применимы (для граждан РФ — 152-ФЗ) и где допустимо хранить и обрабатывать данные: сейчас VPS и провайдер LLM за рубежом, поэтому в демо используются только вымышленные данные. Свести в одну политику жизненный цикл данных: неактивная сессия удаляется через 14 дней, «Удалить мои данные» — сразу, но бэкапы держат её ещё до 7 дней, удалённые копии — 30 дней и дольше в git-истории; план и чат передаются внешнему провайдеру модели.
- **Качество агента.** Порог качества eval-набора как гейт при смене модели, промпта или SDK (сейчас — еженедельный прогон с issue); предпросмотр изменений плана перед применением больших пакетов (сейчас — подтверждение только для массового удаления и отмена хода после).
- **Наблюдаемость.** История метрик и дашборды, алерты с дежурством вместо issue, трассировка вызовов LLM с задержками и стоимостью.
- **Тесты.** Компонентные тесты связки `GanttView` ↔ SVAR (сейчас она проверяется только e2e); SVAR используется в том числе через поведение внутренних частей библиотеки (подавление клика после перетаскивания, портал подсказки, компактный режим), и обновление версии без полного e2e-прогона опасно.
- **Продукт.** Праздники, типы связей, вехи, мультиисполнители, импорт/экспорт MS Project (через MPXJ отдельным сервисом из-за лицензии LGPL).

## Риски

| Риск | Что снижает риск сейчас | Что остаётся |
|---|---|---|
| Модель по-разному понимает одну и ту же команду, особенно массовую | Операции проверяются сервером атомарно, ход агента отменяется целиком, переспрос при неоднозначности, подтверждение массового удаления, еженедельные eval-диалоги | Ошибка «правильная по форме, неверная по смыслу» (не та задача) проходит валидацию; ловит её только пользователь |
| Расход на LLM в публичном демо без входа | Лимиты по сессии, IP и приложению в целом, бюджет токенов на ход, алерт на расход за сутки | Нужен жёсткий лимит расходов на самом ключе у провайдера — последняя защита, если лимиты приложения обойдут |
| Prompt injection через план, Excel или внешний MCP | Ущерб ограничен своей сессией; массовое удаление подтверждает только человек; всё откатывается отменой | Агент может выполнить вредную, но мелкую правку из текста задачи |
| Зависимость от провайдера LLM | Слой `backend/app/agent/llm.py`: прямой Anthropic API или OpenRouter переключаются настройкой | Промпт и контракт инструментов заточены под Claude; смена семейства моделей потребует прогона eval и правок промпта |
| Сторонняя библиотека диаграммы (SVAR, MIT) | Версия зафиксирована, интерактивность покрыта e2e; запасной вариант в спецификации — DHTMLX Community | Часть поведения опирается на детали реализации SVAR, которые могут измениться в любом обновлении |
| Один VPS, общий с другими сервисами | Health-check и автоперезапуск, бэкапы с проверкой восстановления, runbook | Отказ хоста — простой до ручного восстановления на новом сервере; потеря данных — до суток, если цепочка удалённых копий исправна (её сбой основной мониторинг сейчас не видит) |

## Порядок закрытия

**P0** — нельзя открывать для реальных пользователей без этого; **P1** — нужно для надёжной работы при росте; **P2** — по запросу пользователей.

| # | Что | Приоритет | Почему здесь |
|---|---|---|---|
| 1 | Жёсткий лимит расходов на ключе LLM у провайдера | P0 | Пять минут работы, закрывает самый дорогой сценарий злоупотребления |
| 2 | Исправить известные дефекты P1: конфликт правок в карточке, дорогое удаление задачи с множеством связей, алерт на удалённый бэкап, гейт «CI зелёный» для ручного деплоя | P0 | Тихая потеря правки, деградация сервиса одним запросом и выкатка в обход проверок недопустимы с реальными данными; всё локально и не меняет архитектуру |
| 3 | Цели надёжности и дежурство: SLO, RTO/RPO, кто и за сколько реагирует на алерт | P0 | Без целей нельзя решить, достаточно ли одного хоста и ночного дампа; ориентиры — ниже |
| 4 | Учётные записи, владение планами и права; OAuth 2.1 для MCP | P0 | Без этого нельзя хранить чужие данные и давать доступ нескольким людям; меняет модель данных, поэтому раньше масштабирования |
| 5 | Юридический контур данных: где хранятся и обрабатываются, 152-ФЗ, политика удаления и сроков хранения бэкапов | P0, если будут персональные данные | Определяет хостинг и провайдера модели — дешевле решить до миграции пользователей |
| 6 | Бэкапы в хранилище с object lock, резервный хост или managed PostgreSQL | P1 | Сейчас копии есть и проверяются, но их можно удалить с сервера, а отказ хоста — это ручное восстановление |
| 7 | Состояние из памяти процесса — в Postgres/Redis, несколько воркеров | P1 | Первое, во что упрётся рост одновременных пользователей |
| 8 | Метрики, дашборды, трассировка LLM, дежурство; SLO и регулярный нагрузочный прогон | P1 | Нужны раньше роста, чтобы замечать деградацию до пользователей |
| 9 | Порог качества агента на eval-наборе как гейт; компонентные тесты `GanttView` | P1 | Делают безопасными смену модели и обновление SVAR |
| 10 | Дефекты P2, строгий CSP | P2 | Неудобства и усиление защиты без прямого ущерба |
| 11 | Праздники, типы связей, вехи, мультиисполнители, нормализация хранения, MS Project | P2 | Расширения модели — по реальным требованиям, а не заранее |

### Ориентиры для целей надёжности

Предлагаемые стартовые значения для пункта 3 — их нужно утвердить под реальную нагрузку и бюджет:

- **Доступность** 99,5 % в месяц (около 3,5 часа простоя), считая по внешней проверке `/healthz`.
- **Задержка** p95 < 300 мс для API без чата; для хода агента — время до первого события < 5 с (ответ модели целиком зависит от провайдера).
- **RPO** — до 1 часа: к ночному дампу добавить непрерывное архивирование WAL или managed PostgreSQL с point-in-time recovery; сейчас — до суток.
- **RTO** — до 4 часов на новом хосте по runbook; проверять учебным восстановлением раз в квартал, а не только проверкой дампа.
- **Реакция на алерт** — дежурный с оповещением (не только issue в GitHub), подтверждение в течение 30 минут в рабочее время.
