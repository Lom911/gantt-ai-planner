# Roadmap to production

Этот документ описывает: что в текущей реализации — осознанный технический долг (принят ради срока в 2–3 дня), чего не хватает для реального продакшена, какие риски у решения в целом и в каком порядке имеет смысл закрывать долг. Ссылки на код и раздел «Ограничения» — в `README.md`; полная спецификация — в `docs/superpowers/specs/2026-09-25-gantt-ai-planner-design.md`.

## Осознанный технический долг

Ограничения, принятые сознательно ради сроков — не баги, а выбор объёма:

| Ограничение | Почему принято сейчас |
|---|---|
| Один uvicorn-воркер, шина событий (SSE) и блокировка сессии — в памяти процесса | Демо на один-два одновременных пользователя не требует горизонтального масштабирования; `LISTEN/NOTIFY` через Postgres — прямой путь вперёд, но лишняя сложность для MVP |
| Только рабочие дни, без праздничного календаря | Праздники варьируются по стране/региону и требуют отдельного источника данных; для демо-плана не критично |
| Только зависимости «конец → начало» (FS), без SS/FF/SF и отрицательного лага | В большинстве реальных Ганта-планов FS покрывает основной поток; остальные типы связей — это отдельная ветка в планировщике (CPM) и в UI рисования связей |
| Нет вех (задач нулевой длительности) | В модели `duration: int (1..999)` веха — вырожденный случай, требующий отдельной обработки в раскладке и в Excel-формате |
| Один исполнитель на задачу, без мультиисполнителей | Расчёт «перегрузки» и модалка задачи рассчитаны на одного `assignee`; мультиисполнители умножают эту логику |
| План хранится целиком как JSONB-снимок, без отдельных таблиц задач | При лимите 500 задач на план это проще и быстрее в разработке, чем нормализованная схема; отмена/повтор — просто переключение указателя на версию |
| Сессии по cookie без аутентификации, план не расшаривается между пользователями | Соответствует формату «публичное демо»; полноценные учётные записи и совместные планы — это отдельная модель данных (владение, права доступа) |
| Нет офсайт-бэкапов (только план на локальный `pg_dump` на VPS, см. спецификацию §13) | Бэкап-скрипт (`deploy/backup.sh`) и его расписание (cron, установлен `deploy/bootstrap.sh`) уже развёрнуты на проде; офсайт-копия (S3-совместимое хранилище, restic) — отдельная работа, не входившая в первый деплой |

## Чего не хватает для продакшена

### Надёжность и масштабирование

- **`LISTEN/NOTIFY` в Postgres + несколько воркеров uvicorn.** Сейчас шина событий (`backend/app/services/events.py`) и блокировка сессии на время хода агента (`backend/app/services/locks.py`) — это `asyncio`-примитивы внутри одного процесса. Чтобы поднять больше одного воркера или несколько инстансов за балансировщиком, события нужно публиковать через Postgres (`LISTEN/NOTIFY` или отдельную очередь), а блокировку — через advisory lock в БД или Redis.
- **Нагрузочные тесты.** Нет ни одного профиля нагрузки (сколько сессий/сообщений в чат в секунду держит текущая конфигурация лимитов и `mem_limit` контейнеров). Нужно определить целевую нагрузку и прогнать хотя бы базовый сценарий (k6/locust) перед реальным трафиком.

### Модель предметной области

- **Праздники и рабочие календари** — расширение `backend/app/domain/calendar.py` источником праздничных дат. Конкретный кандидат: библиотека `workalendar` (MIT, активно поддерживается) — у неё есть готовый производственный календарь РФ (перенос выходных, праздники), что закрывает основной пробел без ручного ведения списка дат; понадобится только доложить дни на годы вперёд и решить, как обновлять календарь при выходе новых постановлений о переносе выходных.
- **SS/FF/SF-зависимости и отрицательный лаг** — расширение планировщика CPM (`backend/app/domain/scheduler.py`) и операций (`backend/app/domain/operations.py`), плюс UI для выбора типа связи при рисовании (сейчас диаграмма умеет рисовать только FS — см. README, раздел «Диаграмма Ганта: интерактивность»).
- **Вехи** — нулевая длительность как отдельный тип задачи в модели, расчётах и в Excel-формате.
- **Мультиисполнители** — смена модели `Task.assignee: str | null` на список, пересчёт логики перегрузки и модалки задачи.
- **Нормализация задач в БД при росте.** Пока план — один JSONB-снимок на версию (лимит 500 задач). Если лимит вырастет на порядок или понадобятся выборочные запросы/индексы по полям задач, план нужно нормализовать в отдельные таблицы `tasks`/`dependencies` с миграцией существующих версий.
- **Импорт/экспорт MS Project (`.mpp`/`.xml`).** Сейчас единственный формат обмена — Excel (`backend/app/excel/`). Чтение/запись формата MS Project реалистичнее всего через библиотеку MPXJ (LGPL-2.1): лицензия обязывает либо динамически подключать её как отдельный процесс/сервис (например, JVM-сайдкар с HTTP/CLI-интерфейсом конвертации, вызываемый из backend), либо статически линковать с раскрытием исходников связывающего кода — для этого проекта на Python/FastAPI подходит только первый вариант, встраивать MPXJ прямо в код backend не стоит.

### Независимая проверка CPM

- **NetworkX как тестовый эталон.** Планировщик CPM (`backend/app/domain/scheduler.py`) перепроверен на ~200 случайных DAG-планах независимым расчётом через NetworkX (BSD-3, dev-only зависимость `backend/pyproject.toml`) — построением графа в индексах рабочих дней и поиском самого длинного пути (`backend/tests/unit/test_scheduler_crosscheck.py`). NetworkX не умеет проверять SNET-ограничения (`constraint_start`), поэтому эти случаи остаются под отдельными ручными проверками в том же файле.

### UX агента

- **Предпросмотр и подтверждение пакета операций перед применением.** Сейчас у агента уже есть грубое подтверждение для рискованных массовых правок (`ConfirmationRequired`, `backend/app/domain/errors.py`, `requires_confirmation` в `backend/app/domain/operations.py`) — это текстовое «да/нет» в чате без визуализации самой правки. Более безопасный UX — показывать пользователю diff плана (что добавится/удалится/сдвинется) до применения пакета операций и коммита новой версии, а не полагаться только на текстовое подтверждение для больших изменений; технически ближе всего к уже существующему сравнению версий для undo/history (`backend/app/domain/diff.py`), только показанному пользователю превентивно, а не постфактум.

### Многопользовательский режим

- **Аутентификация и общие планы.** Сейчас идентификация — это непрозрачный cookie-токен без пароля/логина; нет модели владения планом и прав доступа (просмотр/редактирование для нескольких людей на одном плане). Нужны: учётные записи, приглашения в план, разграничение прав.

### MCP

- **OAuth 2.1 для внешнего MCP.** Внешний доступ по `/mcp` (Streamable HTTP) реализован, но авторизация — статический Bearer-токен (`mcp_<token>`), выпущенный вручную в UI («Подключить MCP») и живущий до 7 дней, — упрощение для одного пользователя на сессию. Для реального многопользовательского сценария и для соответствия актуальным ожиданиям MCP-клиентов нужен полноценный OAuth 2.1 (authorization code + PKCE), а не долгоживущий статический токен.

### Наблюдаемость

- **Мониторинг, алерты, трейсинг вызовов LLM.** Сейчас логируется только `session_id` (префикс), маршрут, статус и время ответа (`backend/app/logging_setup.py`) — без метрик (Prometheus/аналог), без алертов на рост ошибок/задержек LLM, без трейсинга цепочки «сообщение → вызовы инструментов → ответ» для отладки конкретного хода агента.

### Эксплуатация LLM

- **Регулярный eval-набор промптов на живой LLM.** Ручной smoke-тест на проде прошёл на настоящей модели через OpenRouter (`anthropic/claude-sonnet-5`) — массовый сдвиг задач, назначение исполнителя по неполному имени, добавление задачи с зависимостью, переспрос при неоднозначной команде, подтверждение перед массовым удалением (подробности — `docs/ai-usage.md`, 2026-09-26). Это разовая ручная проверка, не регресс: Playwright e2e (`frontend/e2e/main.spec.ts`, джоб `e2e` в CI) по-прежнему работает на `LLM_PROVIDER=fake` — детерминированно и без затрат, но не проверяет реальное поведение модели. Нет набора эталонных диалогов с ожидаемыми вызовами инструментов/результатами и нет расписания повторного прогона на живой модели при смене модели, промпта или версии SDK.

### Хостинг и соответствие

- **Хостинг в РФ под 152-ФЗ.** Текущий план — VPS не в РФ, LLM — внешний API Anthropic; обработка и хранение персональных данных граждан РФ в таком контуре не проработана и не разрешена без изменения архитектуры (хостинг и, вероятно, локальная модель — в РФ). Сейчас это закрыто эксплуатационно: в демо используются только вымышленные данные (см. README, «Безопасность и данные»).
- **Офсайт-бэкапы (restic).** Реализован только локальный `pg_dump -Fc` на самом VPS (`deploy/backup.sh`) с хранением 7 дней; копия на внешнее хранилище (S3-совместимое, через restic) не реализована.

### Безопасность

- **CSP без `unsafe-inline`.** Текущая политика Caddy (`deploy/caddy/Caddyfile`) допускает `style-src 'self' 'unsafe-inline'` — уступка Tailwind/inline-стилям сторонних компонентов (в частности SVAR). Для более строгой политики нужны либо nonce/hash для стилей, либо отказ от инлайн-стилей в зависимостях.
- **Rootless Docker.** Контейнер приложения уже запускается непривилегированным пользователем (uid 10001, `read_only`, `cap_drop: ALL`), но сам Docker-движок на VPS работает как обычно (root daemon). Полностью rootless-режим Docker на хосте — отдельная работа по настройке сервера, не сделанная в рамках `deploy/bootstrap.sh`.

- **Остаток аудита безопасности 2026-09-26** (исправленное — в `docs/ai-usage.md`):
  - деплой по digest образа (`tag@sha256:…` с проверкой в `planner-deploy`) вместо изменяемого тега, required reviewers на окружении `production`;
  - отдельная internal-сеть Caddy↔app вместо общей `edge`, чтобы соседние контейнеры не могли обойти Caddy и подделать `X-Forwarded-For`;
  - снимок БД перед автоматической миграцией в `planner-deploy`, алерт на сбой cron-бэкапа, офсайт-копия с шифрованием; откат образа после необратимой миграции сейчас не сработает;
  - бюджет хода агента в токенах по `usage` (сейчас — только лимит итераций и обрезка результатов инструментов), резерв дневной квоты для новых пользователей;
  - `pids_limit`, `size=` для tmpfs, hardening контейнера `db`; `npm audit` в CI; пороги Trivy ниже CRITICAL.

### Тестирование

- **Компонентные тесты на связку `GanttView`.** Юнит-тесты покрывают чистую логику интерпретации drag/resize/link (`frontend/src/components/gantt/interactions.test.ts`, `mapping.test.ts`), но нет теста, монтирующего сам `GanttView` и проверяющего, что события SVAR (`update-task`, `add-link`, `show-editor`) действительно долетают до `onApply`/`onOpenTask` и что отклонённая правка откатывает бар (`revision`/`snapBack`) — сейчас это проверяется только вручную и через e2e-сценарий целиком.

## Риски

| Риск | Пояснение | Что снижает риск сейчас |
|---|---|---|
| Недетерминированность LLM | Модель может по-разному интерпретировать одну и ту же команду, особенно при массовых правках | Атомарные пакеты операций с серверной валидацией, отмена целого хода агента, ручной чек-лист перед сдачей — но не полноценный eval-набор (см. выше) |
| Стоимость вызовов LLM | Публичное демо без аутентификации может привлечь нежелательную нагрузку на платный API | Лимиты на чат (30 сообщений/час на сессию, 500/сутки на всё приложение), `max_tokens` на ответ, отдельный workspace/ключ Anthropic с лимитом расходов |
| Зависимость от одного LLM-провайдера | Весь агент построен на Anthropic SDK и конкретном формате инструментов; смена провайдера — не тривиальная замена одной переменной | Слой `backend/app/agent/llm.py` абстрагирует вызов модели и позволяет добавить второй адаптер, но контракт инструментов и промпт написаны с оглядкой именно на Claude |
| Баги/ограничения SVAR Gantt | Сторонняя библиотека, теперь используется и для drag/resize/рисования связей, а не только для отображения (в частности, риск рассинхронизации шапки/таблицы или зависаний прокрутки, по опыту схожих проектов) | Версия зафиксирована (`2.7.3`), в спецификации записан запасной вариант — DHTMLX Community v10 (MIT); отклонённая правка откатывается тостом + возвратом бара (`snapBack`), но нет отдельных компонентных тестов на саму связку SVAR ↔ `GanttView` (см. «Чего не хватает», раздел «Тестирование») |
| Единственный VPS (single point of failure) | Один сервер держит и БД, и приложение, и reverse proxy; простой VPS = простой сервиса | Health-check и `restart: unless-stopped`, локальные бэкапы БД — но без резервного хоста и без офсайт-бэкапов (см. выше) отказ диска/провайдера теряет данные |

## Порядок закрытия

Приоритеты: **P0** — блокирует реальную эксплуатацию с настоящими пользователями/данными; **P1** — заметно повышает надёжность/качество, но сервис работоспособен без этого; **P2** — улучшения, которые можно откладывать надолго.

| # | Что | Приоритет | Почему в этом порядке |
|---|---|---|---|
| 1 | Мониторинг, алерты и трейсинг вызовов LLM | **P0** | Без наблюдаемости невозможно вовремя заметить деградацию модели, рост ошибок или аномальный расход API — а именно это самый дорогой и самый непредсказуемый ресурс сервиса |
| 2 | Офсайт-бэкапы (restic) и проверка восстановления не «один раз вручную», а по расписанию | **P0** | Единственный VPS без внешней копии данных — это гарантированная потеря данных при первом серьёзном инциденте с диском/хостом |
| 3 | `LISTEN/NOTIFY` в Postgres + несколько воркеров uvicorn | **P1** | Нужно только при реальном росте одновременных пользователей; для текущего масштаба (демо/тестовое) риск невелик, но это первое, что упрётся в потолок при успехе продукта |
| 4 | Аутентификация и общие планы | **P1** | Меняет модель данных и права доступа — крупная работа, но без неё сервис остаётся демо для одного анонимного пользователя за раз, что ограничивает реальное применение |
| 5 | OAuth 2.1 для внешнего MCP | **P1** | Внешний `/mcp` уже работает на статическом токене — это допустимо для одного пользователя на сессию, но не для реального многопользовательского сценария |
| 6 | Нагрузочные тесты | **P1** | Нужны, чтобы осознанно выставлять лимиты и `mem_limit`, но без них сервис не небезопасен — просто конфигурация подобрана на глаз |
| 7 | Регулярный eval-набор промптов на живой LLM + e2e не только на fake-LLM | **P1** | Разовый ручной smoke-тест на проде прошёл (см. `docs/ai-usage.md`, 2026-09-26), но повышает уверенность в качестве агента при смене модели/промпта именно повторяемый прогон; отсутствие не блокирует работу сегодня, но усложняет безопасные будущие изменения |
| 8 | Компонентные тесты на связку `GanttView` (события SVAR → операции, откат по `snapBack`) | **P1** | Сейчас это самый интерактивный и наименее покрытый тестами узел UI — регресс здесь сегодня ловит только e2e целиком или ручная проверка |
| 9 | Праздники/календари, SS/FF/SF и отрицательный лаг, вехи, мультиисполнители | **P2** | Расширения модели предметной области, ценность зависит от реальных требований пользователей — делать по запросу, а не заранее |
| 10 | Нормализация задач в БД | **P2** | Оправдана только при заметном росте лимита задач на план или потребности в выборочных запросах — сейчас 500 задач в одном JSONB достаточно |
| 11 | Хостинг в РФ под 152-ФЗ | **P2** (переходит в P0, если появятся реальные ПДн) | Пока используются только вымышленные данные, это не блокер; становится обязательным условием ровно в момент, когда в план попадут настоящие персональные данные граждан РФ |
| 12 | CSP без `unsafe-inline`, rootless Docker | **P2** | Дополнительное усиление защиты сверх уже принятых мер (непривилегированный пользователь в контейнере, `cap_drop: ALL`, `read_only`); риск от их отсутствия ниже, чем у пунктов выше |
