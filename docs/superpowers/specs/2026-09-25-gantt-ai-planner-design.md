# Gantt AI Planner — спецификация

- Дата: 2026-09-25
- Статус: черновик на ревью
- Основание: ТЗ «Full-stack разработчик AI-native продукта (React + FastAPI)» и 5 раундов согласования решений с автором

## 1. Цель и критерии успеха

Пользователь открывает страницу и сразу видит интерактивную диаграмму Ганта с демо-планом. Рядом с ней находится чат: на естественном языке можно массово править план (переносить задачи, менять зависимости, добавлять задачи, переназначать исполнителей). Изменения агента сразу видны на диаграмме. По клику на задачу открывается модалка. План загружается из Excel и выгружается обратно в Excel.

Обязательный стек: React, Python/FastAPI, MCP, LLM через API.

**Что сдаём** (всё обязательно, в урезание не попадает):

1. Публичный репозиторий `github.com/Lom911/gantt-ai-planner`.
2. Развёрнутое приложение: `https://gantt-ai-planner.duckdns.org`.
3. README: как запустить, архитектура, принятые решения, отдельный раздел об использовании AI-ассистентов.
4. Демо-gif и mp4 основного сценария: загрузка Excel → правка через чат → экспорт.
5. Пример Excel: `examples/sample-plan.xlsx`.
6. Документ `docs/roadmap-to-production.md`.

**Критерии успеха:**

- Первая загрузка страницы показывает демо-план без холодного старта.
- Сценарий «загрузка → чат → экспорт» стабильно проходит вживую.
- Экспортированный файл загружается обратно без потерь.
- MCP реально участвует в работе агента, а не подключён для галочки.

## 3. Архитектура

```
Browser (React SPA)
  ├─ REST  /api/*            ─┐
  ├─ SSE   /api/chat (stream) │
  └─ SSE   /api/events        │     External MCP client (Claude Code/Desktop)
                              ▼             │  Streamable HTTP + Bearer mcp_…
┌──────────────────────── FastAPI (1 uvicorn worker) ────────────────────────┐
│ api/        routers, session cookie middleware, rate limits                 │
│ agent/      agent loop (Anthropic SDK) ──► in-process MCP client ──┐        │
│ mcp/        FastMCP server "planner" (tools) ◄─────────────────────┴─ /mcp  │
│ services/   PlanService: load → apply ops → schedule → save version → emit  │
│ domain/     models, scheduler (CPM), operations, validation, diff (pure)    │
│ excel/      import parser, export writer (pure)                             │
│ events/     in-process per-session pub/sub → SSE                            │
│ db/         SQLAlchemy 2 models, repositories, Alembic                      │
└─────────────────────────────────────────────────────────────────────────────┘
                              │ asyncpg
                        PostgreSQL 17
```

**Принципы:**

- `domain/` и `excel/` — чистый Python без ввода-вывода: не знают о БД, HTTP и LLM. Всё сложное (расписание, операции, разбор файлов) живёт здесь и полностью покрыто юнит-тестами.
- `PlanService` — единственный путь изменить план. Правка из интерфейса, агент и внешний MCP используют один и тот же вызов `apply(session, ops, source)`.
- Источник правды для дат — бэкенд. Фронтенд только отображает вычисленные даты и отправляет на бэкенд намерения («сдвинуть», «растянуть», «связать»).
- Бэкенд работает в одном процессе uvicorn: шина событий хранится в памяти процесса. Это ограничение явно описано в README и Roadmap, там же путь дальше: LISTEN/NOTIFY в Postgres.

## 4. Модель предметной области

### 4.1. Входное состояние плана (хранится)

```
Plan
  project_start: date                 # всегда рабочий день
  tasks: [Task]                       # порядок = порядок строк в таблице
  dependencies: [Dependency]

Task
  id: int                             # стабильный, уникален в плане; в Excel это «№»
  name: str (1..200)
  description: str (0..2000)
  assignee: str | null (0..100)
  duration: int (1..999)              # рабочие дни
  constraint_start: date | null       # SNET — «начать не раньше»

Dependency                            # только FS
  predecessor_id: int
  successor_id: int
  lag: int (0..365)                   # рабочие дни
```

- Новые задачи получают `id = max(id) + 1`. После удаления номера не переиспользуются и не перенумеровываются.
- Названия задач могут повторяться.
- Обе стороны зависимости должны существовать. Дублировать зависимости и связывать задачу саму с собой нельзя.

### 4.2. Вычисляемое состояние (не хранится, считается при каждом чтении)

Для каждой задачи вычисляются:
- `start`, `end` — даты включительно;
- `slack` — резерв в рабочих днях;
- `is_critical`;
- `constrained_by` — чем определено начало: `project_start`, `constraint` или `predecessor:<id>`;
- `overallocated_with` — ID задач того же исполнителя с пересекающимися датами.

Для плана вычисляются `project_end` и `critical_path` (ID задач).

### 4.3. Календарь и расписание

- Рабочие дни — понедельник–пятница, праздников нет. Если дата попадает на выходной, она сдвигается на следующий рабочий день.
- Задача длительностью `d` занимает `d` рабочих дней: `end = add_workdays(start, d − 1)`.
- **Прямой проход.** Задачи обходятся в топологическом порядке (алгоритм Кана, при цикле выдаётся ошибка со списком задач цикла). Начало задачи — наибольшая из трёх дат:
  - `project_start`;
  - `constraint_start` (сдвинутая на рабочий день);
  - для каждого предшественника: `add_workdays(pred.end, 1 + lag)`.
- **Обратный проход** идёт от `project_end`. Позднее окончание задачи — наименьшая из дат `sub_workdays(succ.late_start, 1 + lag)` по всем последователям; если последователей нет, это `project_end`. Резерв `slack` — число рабочих дней от `start` до позднего начала. Задача критическая, если `slack == 0`.
- **Перегрузка исполнителя:** две задачи с одинаковым непустым `assignee`, у которых пересекаются отрезки `[start, end]`.
- Нулевая длительность (вехи), отрицательный лаг, зависимости SS/FF/SF и праздники не поддерживаются. Всё это записано в Roadmap.

## 5. Операции

Одна схема операций (Pydantic, с разделением по полю `op`) используется в API, в инструментах MCP и в тестах. Пакет операций **атомарен**: операции применяются по очереди к копии плана, затем проверяются инварианты и выполняется пересчёт. Если что-то не так, пакет отклоняется целиком, а в ответе указано, какая операция и почему не прошла.

| `op` | Параметры | Семантика |
|---|---|---|
| `add_task` | `name, description?, assignee?, duration, predecessors?: [{id, lag?}], after_id?` | Новая задача. Встаёт после `after_id` или в конец. Возвращает новый `id` |
| `update_task` | `id, name?, description?, assignee?, duration?` | Переназначение — это `update_task` с полем `assignee` (пустая строка снимает исполнителя) |
| `move_task` | `id, start_date? \| shift_days?` | Ставит ограничение «не раньше» (`shift_days` считается от текущего вычисленного `start`, в рабочих днях). Если предшественники не дают сдвинуть так рано, ограничение сохраняется, но в результате будет предупреждение `limited_by_predecessor` |
| `clear_constraint` | `id` | Снимает ограничение «не раньше» |
| `set_dependencies` | `id, predecessors: [{id, lag?}]` | Полностью заменяет список предшественников задачи |
| `add_dependency` | `predecessor_id, successor_id, lag?` | Добавляет одну связь |
| `remove_dependency` | `predecessor_id, successor_id` | Удаляет одну связь |
| `delete_task` | `id` | Удаляет задачу. Её последователи получают её предшественников («мост»), лаг берётся как `lag_in + lag_out`, при этом дубли связей схлопываются, а из нескольких лагов остаётся наибольший. Мост показывается в diff |
| `set_project_start` | `date` | Меняет дату старта проекта |

Результат применения пакета:
- новая версия плана;
- **diff** со списком `{task_id, field, before, after}`, в котором есть и сдвиги вычисленных дат (`start`/`end`);
- предупреждения.

## 6. Сессии, версии, отмена

- **Сессия.** При первом запросе к API без cookie создаётся сессия с копией демо-плана. Cookie `__Host-sid` содержит 256-битный непрозрачный токен и выставляется с флагами `HttpOnly; Secure; SameSite=Lax; Path=/`. В БД хранится `sha256(token)`. В локальной разработке по HTTP cookie называется `sid` и выставляется без `Secure`, это регулируется флагом в конфиге.
- **Версии.** Каждое успешное применение пакета сохраняет снимок **входного** состояния плана как новую версию. Поля версии:
  - `version_no`;
  - `source`: `seed | import | user | agent | mcp | reset`;
  - `turn_id` (для ходов агента);
  - `summary`;
  - `diff` (JSONB).
- **Указатель.** `sessions.current_version` указывает на текущую версию.
- **Отмена и повтор.** Отмена (undo) переносит указатель на предыдущую **группу** версий. Группа — это все версии одного хода агента (общий `turn_id`) или одна отдельная версия. Повтор (redo) переносит указатель вперёд. Новая правка после отмены удаляет «будущие» версии.
- **Лимит.** Не больше 50 версий на сессию, самые старые удаляются.
- **История задачи** (фаза 3) вычисляется из `diff` сохранённых версий.
- **Сброс к демо** (`reset`) создаёт новую версию из демо-шаблона. Её тоже можно отменить.

## 7. Агент

- **SDK и модели.** Используется `anthropic` (официальный Python SDK). Модель по умолчанию `claude-sonnet-5`, запасная `claude-haiku-4-5-20251001`, выбирается через `LLM_MODEL`. Первая задача фазы 1 — smoke-тест модели на настоящем ключе.
- **Как устроен ход.** Сообщение пользователя приходит в `POST /api/chat`, ответ стримится через SSE. Агент выполняет цикл:
  1. Сообщение отправляется в LLM, ответ стримится.
  2. Если модель просит вызвать инструмент, вызов идёт через MCP-клиент внутри процесса.
  3. Результат инструмента возвращается модели.
  4. Цикл повторяется до финального ответа, но не больше 15 итераций.
- **Контекст хода:**
  - системный промпт: роль агента, правила, сегодняшняя дата, правила про неоднозначность и разрушительные действия;
  - список инструментов;
  - **компактная таблица текущего плана** (`id | задача | исполнитель | длит | предш | начало | конец | резерв | флаги`);
  - последние 20 текстовых сообщений текущего диалога (см. «Чат» в разделе интерфейса: открытие страницы и «Очистить» начинают новый диалог). Следы вызовов инструментов в историю не попадают: актуальный план и так передаётся каждый ход.
- **Кэширование.** Системный промпт и инструменты кэшируются (prompt caching).
- **Правила поведения** (задаются системным промптом и проверяются на сервере):
  - Изменения применяются сразу, отдельного подтверждения не нужно.
  - Если по названию подходит несколько задач, агент переспрашивает.
  - Если один ход удаляет больше 5 задач или больше 50% плана, агент сначала спрашивает. На сервере это гарантируется так: если пакет удаляет слишком много задач, `apply_operations` отклоняет его с ошибкой `confirmation_required`, и агент обязан переспросить пользователя. После подтверждения агент повторяет вызов с `confirmed: true`.
- **Каждый вызов `apply_operations` сохраняет версию** с общим `turn_id` и отправляет событие `plan_changed`. Поэтому диаграмма обновляется прямо во время хода, а отмена откатывает весь ход целиком.
- **События стрима чата:**
  - `text_delta`;
  - `tool_started {name}`;
  - `tool_finished {name, ok, summary}`;
  - `plan_changed {version}`;
  - `done {turn_id, diff_summary}`;
  - `error {code, message}`.
- **Ошибки:**
  - Ошибка валидации операций возвращается модели как ошибка инструмента, модель может исправиться.
  - При ошибке LLM (429/529/таймаут 60 с на запрос, 180 с на весь ход) пользователь видит сообщение. Уже сохранённые версии хода остаются, их можно отменить.
- **Инвариант:** пока идёт вызов LLM, транзакция БД не открыта.
- **Лимиты** считаются по таблице сообщений в БД, поэтому переживают рестарт:
  - 30 сообщений пользователя в час на сессию;
  - 500 в сутки на всё приложение;
  - `max_tokens` на ответ.
  При превышении возвращается `429` с понятным текстом.
- **Параллельные изменения.** На каждую сессию есть `asyncio.Lock`, все изменения выполняются под ним. Пока идёт ход агента:
  - правки из интерфейса получают `409 agent_busy`, а сам интерфейс блокирует диаграмму;
  - внешний MCP ждёт освобождения блокировки до 10 с, потом получает ошибку.
- **Тестовый режим.** Поддельный LLM (`LLM_PROVIDER=fake`) работает по детерминированным сценариям: ищет ключевые фразы и выдаёт заранее заданные вызовы инструментов. Он используется по умолчанию локально без ключа, в e2e-тестах и при записи демо.

## 8. MCP

- **Библиотека.** FastMCP, сервер называется `planner`. Какой пакет и какая версия (`fastmcp` отдельно или `mcp.server.fastmcp` из официального SDK), решается в начале плана по актуальной документации. Требования к выбранному варианту: должен быть клиент внутри процесса, приложение для Streamable HTTP, которое монтируется в FastAPI, и точка, где можно проверить токен.
- **Инструменты:**

| Инструмент | Что делает |
|---|---|
| `get_plan()` | Компактная таблица плана и сводка (даты проекта, критический путь, конфликты) |
| `find_tasks(query?, assignee?, critical_only?)` | Поиск задач |
| `get_task(id)` | Задача, её связи и вычисленные поля |
| `get_resource_load(assignee?)` | Загрузка по исполнителям, пересечения |
| `apply_operations(ops, confirmed?)` | Атомарный пакет операций (раздел 5) |
| `undo()` | Отменить последнюю группу изменений |

- **Сессию определяет транспорт, а не аргументы инструмента.** Для клиента внутри процесса сессия берётся из контекста хода, для HTTP — из токена. У инструментов **нет** параметра `session_id`, поэтому ни LLM, ни внешний клиент не может обратиться к чужому плану.
- **Внешний доступ (фаза 2).** `/mcp` доступен по Streamable HTTP с заголовком `Authorization: Bearer mcp_<token_urlsafe(32)>`.
  - Токен выпускается в диалоге «Подключить MCP» и показывается один раз.
  - В БД хранятся `sha256` и префикс токена.
  - Токен привязан к одной сессии и живёт до 7 дней; его можно отозвать и перевыпустить.
  - Токены в query string не принимаются, заголовок `Origin` проверяется.
  - В диалоге есть готовый фрагмент для `claude mcp add --transport http …` и JSON для Claude Desktop.
- **Изменения через внешний MCP** сохраняются с `source=mcp` и сразу приходят в браузер через `/api/events`.

## 9. Excel

### 9.1. Импорт

- **Формат:** `.xlsx`, до 2 МБ, читается первый лист. Используется `openpyxl` в режиме только для чтения, `defusedxml` установлен.
- **Строка заголовков** — первая строка, в которой найдена колонка задачи. Сравнение без учёта регистра и пробелов, по синонимам:
  - `№`: `№`, `#`, `id`, `номер`;
  - задача: `задача`, `название`, `наименование`, `task`, `name`;
  - описание: `описание`, `description`;
  - исполнитель: `исполнитель`, `ответственный`, `assignee`, `owner`, `resource`;
  - длительность: `длительность`, `дни`, `duration`, `days`;
  - предшественники: `предшественники`, `зависимости`, `predecessors`, `depends on`;
  - необязательная колонка «Не раньше»: `не раньше`, `начать не раньше`, `snet`, `start no earlier than`. Даты в ней становятся `constraint_start`.
- Обязательны колонки задачи и длительности. Остальные колонки необязательны, неизвестные игнорируются. Пустые строки пропускаются.
- **Длительность:** `5`, `5д`, `5 д.`, `5 дн`, `5 дней`, `5d`, `1 нед`, `1w` (неделя = 5 рабочих дней). Дробное значение округляется вверх, это предупреждение. Пустое значение или 0 превращаются в 1 с предупреждением.
- **Предшественники.** Элементы разделяются `,` или `;`, у каждого необязательный лаг вида `+N`, например `3+2`.
  - Число — это `№`, если колонка `№` есть, иначе порядковый номер задачи в файле (1-based).
  - Текст — название задачи. Если название неоднозначно, это ошибка «укажите №».
- **Ошибки блокируют импорт:**
  - нет обязательной колонки;
  - пустое название;
  - неизвестная ссылка;
  - ссылка на саму себя;
  - цикл;
  - больше 500 задач;
  - повторяющийся `№`.

  Все проблемы собираются в один отчёт с номерами строк и показываются пользователю.
- **Предупреждения** не блокируют импорт.
- **Результат:** при успехе текущий план заменяется целиком, создаётся версия `source=import` (отменяемая), в чат добавляется системное сообщение «Загружен план «<имя файла>», N задач». Дата старта проекта берётся из диалога импорта; по умолчанию это ближайший понедельник по часовому поясу браузера.

### 9.2. Экспорт

- Лист «План» с колонками `№, Задача, Описание, Исполнитель, Длительность, Предшественники, Не раньше, Начало, Окончание, Резерв, Критическая`.
- Предшественники выводятся по `№`, с лагом `+N`.
- Даты записываются как даты Excel. Заголовки выделены жирным, первая строка закреплена, у колонок подобрана ширина.
- Имя файла: `plan-YYYY-MM-DD.xlsx`.
- **Обратная загрузка:** при импорте экспорта `№` сохраняются, лишние колонки игнорируются. Тест проверяет равенство входного состояния, а при той же дате старта и равенство вычисленных дат.
- Колонка «Не раньше» в ТЗ не описана, её добавили мы. Она нужна, чтобы ограничения переживали обратную загрузку. Импорт файла без неё работает как обычно.

## 10. API

| Метод и путь | Назначение |
|---|---|
| `GET /api/plan` | Вычисленный план: `version`, `can_undo`, `can_redo`, `agent_busy` |
| `POST /api/plan/operations` | `{ops}` с `source=user`, возвращает план и diff. `409 agent_busy`, `422` при ошибке валидации |
| `POST /api/plan/undo` · `POST /api/plan/redo` | Отмена и повтор |
| `POST /api/plan/reset` | Сброс к демо |
| `POST /api/plan/import` | multipart: `file`, `project_start`. Возвращает `{ok, plan}` или `{ok:false, errors[], warnings[]}` |
| `GET /api/plan/export` | Файл xlsx |
| `GET /api/plan/tasks/{id}/history` | История задачи (фаза 3) |
| `POST /api/chat` | `{message}` → поток `text/event-stream` (раздел 7) |
| `GET /api/chat/history` | Сообщения текущего диалога с diff-сводками |
| `POST /api/chat/conversations` | Начать новый диалог (открытие страницы, «Очистить»); прежний остаётся в истории, другие вкладки получают событие `chat_reset` |
| `GET /api/chat/conversations` · `GET /api/chat/conversations/{id}` | «История»: прошлые диалоги сессии (последние 50) и сообщения одного из них, только чтение |
| `GET /api/events` | SSE: `plan_changed {version, source, turn_id, changed_task_ids}`, `agent_status {busy}`, heartbeat каждые 20 с |

Для методов, меняющих данные, заголовок `Origin` должен совпадать с `PUBLIC_ORIGIN`. Ошибки возвращаются в едином формате `{error: {code, message, details?}}`.

## 11. Хранилище

PostgreSQL 17, SQLAlchemy 2 (async, asyncpg), миграции Alembic.

```
sessions      (id uuid pk, token_hash bytea unique, current_version int,
               chat_conversation_id uuid, created_at, last_seen_at)
plan_versions (id bigserial pk, session_id fk→sessions on delete cascade,
               version_no int, snapshot jsonb, source text, turn_id uuid null,
               summary text, diff jsonb, created_at,
               unique(session_id, version_no))
chat_messages (id bigserial pk, session_id fk cascade, role text, content text,
               turn_id uuid null, conversation_id uuid null, meta jsonb, created_at)
               index (session_id, created_at), index (created_at),
               index (session_id, conversation_id, created_at)
mcp_tokens    (id uuid pk, session_id fk cascade, token_hash bytea unique,
               prefix text, expires_at, last_used_at, revoked_at, created_at)
```

- План хранится JSONB-снимком целиком, отдельных таблиц для задач нет. В плане до 500 задач, запросов по отдельным задачам нет, а отмена и повтор становятся просто переключением указателя. В Roadmap записано, когда стоит нормализовать.
- **Роли:**
  - `postgres` — только для инициализации;
  - `planner_owner` — владелец схемы, от него выполняет миграции разовый сервис `migrate`;
  - `planner_app` — только SELECT/INSERT/UPDATE/DELETE, лимит соединений 15, `statement_timeout=15s`, `idle_in_transaction_session_timeout=30s`, `lock_timeout=5s`.
- Пул соединений: 5+5, `pool_pre_ping`.
- **Очистка (фаза 2):** фоновая задача в приложении раз в час удаляет сессии, у которых `last_seen_at` старше 14 дней.

## 12. Фронтенд

- **Стек:** Vite, React 19, TypeScript (strict), Tailwind v4, shadcn/ui, TanStack Query; npm.
- **Гантт:** SVAR `@svar-ui/react-gantt` 2.7.3 (MIT), версия закреплена. Обёртка `GanttView`:
  - Преобразует задачи в формат SVAR. В SVAR `end` исключительный, поэтому к дате окончания прибавляется 1 день.
  - Собственный тип задачи `critical` с CSS-классом. Для перегруженных — класс `conflict`.
  - Линия «сегодня» сделана через `highlightTime` и CSS.
  - Русская локаль с исправленными названиями месяцев.
  - `init` вызывается один раз, обработчики передаются через ref, массивы задач и связей мемоизированы.
  - Клик по задаче открывает модалку, встроенный редактор SVAR подавлен (`intercept('show-editor')`).
  - Фаза 2: перетаскивание → `move_task`, растягивание → `update_task{duration}`, рисование связи → `add_dependency`. SVAR сам не пересчитывает расписание, после ответа сервера отображается его версия. При ошибке диаграмма возвращается к прежнему состоянию.
- **Макет.** Верхняя панель:
  - «Загрузить Excel»;
  - «Экспорт»;
  - отменить / повторить;
  - масштаб (день / неделя / месяц) и «Сегодня» (цветом как столбец сегодняшнего дня; прокручивает диаграмму так, чтобы сегодняшний день оказался посередине);
  - «Сбросить к демо»;
  - «Подключить MCP»;
  - меню: «Удалить мои данные», тема.

  Под панелью диаграмма (около 70%) и чат, граница между ними перетаскивается. Ширина меньше 768 px — вкладки «Диаграмма» / «Чат».
- **Чат:**
  - ответ агента появляется по мере генерации;
  - пока работает инструмент, показывается статус;
  - под ответом агента — раскрываемая diff-сводка «Изменено N задач» (было → стало, клик переходит к задаче);
  - подсказки-примеры команд для пустого чата;
  - каждое открытие или перезагрузка страницы начинает новый диалог: чат пустой, агент прежний диалог не помнит (план и отмена не затрагиваются). «Очистить» в заголовке чата делает то же без перезагрузки. Прежние диалоги сохраняются и открываются кнопкой «История» (только чтение). Лимиты чата считают сообщения всех диалогов; вопрос агента о массовом удалении с новым диалогом снимается;
  - пометка «план отправляется в LLM Anthropic, не загружайте реальные персональные данные».
- **Модалка задачи.** Форма: название, описание, исполнитель (выбор из существующих или ввод нового), длительность, ограничение «не раньше» (дата, можно снять). Только для чтения:
  - начало, конец, резерв;
  - признак критической задачи;
  - чем определено начало;
  - предупреждение о перегрузке.

  Там же предшественники и последователи с переходом по клику, а в фазе 3 история задачи. Сохранение отправляет одну операцию `update_task`/`move_task`/`clear_constraint`.
- **Диалог импорта:** файл, дата старта, отчёт об ошибках и предупреждениях с номерами строк.
- **Обновление в реальном времени.** Хук `useSessionEvents` подписан на `/api/events`. По событию `plan_changed` он сбрасывает кэш запроса плана и на 2 с подсвечивает `changed_task_ids`. После переподключения план перезапрашивается.
- **Внешний вид.** Спокойный рабочий интерфейс без шаблонной «ИИ-эстетики» (с опорой на frontend-design), светлая и тёмная темы. Критические задачи красные, перегруженные оранжевые, недавно изменённые подсвечиваются.

## 13. Безопасность и данные

- **Секреты во время работы.** Используются `secrets:` в Compose (файлы монтируются в `/run/secrets`) и `secrets_dir` в pydantic-settings; в коде секреты хранятся как `SecretStr`.
  - Секреты: `anthropic_api_key`, `db_app_password`, `db_owner_password`, `pg_superuser_password`.
  - На хосте: каталог `/opt/gantt-planner/secrets` с правами 0700 (root), файлы 0444.
  - Несекретная конфигурация — в `.env` (0600).
  - Одни и те же ключи не дублируются в `.env`: переменные окружения перекрывают `secrets_dir`.
  - Локально: `.env` в `.gitignore`, `.env.example` в репозитории.
- **CI/CD.** Секретов, которые нужны приложению для работы, в GitHub нет.
  - В GitHub Environment `production` хранятся только `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS` и переменные `DEPLOY_HOST`, `DEPLOY_USER`.
  - Деплой только из `main`, `concurrency: deploy-prod`.
  - Actions закреплены по SHA, `permissions` минимальные, у `checkout` стоит `persist-credentials: false`.
- **Деплой-доступ.** Пользователь `deploy` **не** входит в группу `docker`.
  - Ключ в `authorized_keys` ограничен: `restrict,command="/usr/local/bin/planner-deploy-wrapper"`.
  - Обёртка проверяет тег по шаблону `^sha-[0-9a-f]{7,40}$` и вызывает `sudo /usr/local/bin/planner-deploy <tag>`.
  - `planner-deploy` обновляет `IMAGE_TAG`, затем выполняет `compose pull`, `up -d` и проверку `/healthz`.
- **Проверки в CI:** защита от пуша секретов в GitHub, gitleaks (pre-commit и CI), Dependabot (pip, npm, github-actions, docker), Trivy для образа.
- **Контейнер приложения:**
  - пользователь 10001;
  - `read_only` и tmpfs `/tmp`;
  - `cap_drop: ALL`, `no-new-privileges`;
  - healthcheck, `restart: unless-stopped`;
  - логи json-file 10m×3;
  - `mem_limit`: app 300m, db 256m (`shared_buffers=64MB`, `max_connections=20`), caddy 64m.
- **Образы** закреплены по версии и digest.
- **Caddy:**
  - HSTS `max-age=31536000` без preload;
  - CSP `default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'; base-uri 'self'`;
  - `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`;
  - заголовок `Server` убран;
  - `request_body max_size 5MB`.
- **CORS** не нужен: всё на одном источнике.
- **Логи.** Никаких промптов, содержимого планов, имён людей и тел запросов. Пишется только `session_id` (префикс), маршрут, статус, время ответа и число токенов.
- **Персональные данные:**
  - В демо-данных и примере Excel только вымышленные имена.
  - В интерфейсе и README пометка про отправку данных в Anthropic.
  - Сессии живут 14 дней после последнего визита, бэкапы хранятся не дольше 7 дней.
  - Есть «Удалить мои данные».
  - В Roadmap: 152-ФЗ (хостинг и LLM в РФ для реальных персональных данных граждан РФ), DPIA-lite.
- **Anthropic.** Отдельный workspace и ключ с лимитом расходов и rate limit. Ключ лежит только на сервере.
- **Бэкапы (фаза 2).** Ночной `pg_dump -Fc` от `planner_owner` в `/var/backups/gantt-planner`, хранятся 7 дней. Восстановление проверяется один раз вручную, в `docs/runbook.md` записывается, как это сделать. Копия на внешнее хранилище (restic) записана в Roadmap.
- **Ротация секретов** описана в `docs/runbook.md`: ключ Anthropic, пароли БД, deploy-ключ. При инциденте все секреты отзываются одновременно.

## 14. Деплой

- **Хост.** Собственный VPS: Ubuntu 24.04, 2 vCPU, 1.8 ГБ RAM и 2 ГБ swap, Docker 29, Compose v5, Хельсинки. На нём работают другие сервисы, их не трогаем, ufw не включаем. Внутренние подробности сервера в публичный репозиторий не попадают.
- **Общий reverse proxy.** Отдельный стек `/opt/caddy` (Caddy 2, образ закреплён) в Docker-сети `edge`, Let's Encrypt через HTTP-01. Сайт `gantt-ai-planner.duckdns.org` проксирует запросы в `app:8000`. Поддомен DuckDNS создаёт владелец, A-запись указывает на IP VPS; токен DuckDNS на сервере не нужен.
- **Стек приложения** `/opt/gantt-planner`, compose-проект `gantt-planner`:
  - `db` — postgres:17-alpine, данные в `/var/lib/gantt-planner/pg`, сеть `backend` (`internal: true`), `initdb.d/10-roles.sh` создаёт роли, healthcheck;
  - `migrate` — тот же образ приложения, `alembic upgrade head` от `planner_owner`, запускается один раз при каждом деплое;
  - `app` — FastAPI отдаёт собранный SPA, uvicorn с 1 воркером, сети `backend` и `edge`, стартует после `service_completed_successfully` сервиса `migrate`.
- **Образ.** Один multi-stage Dockerfile: `node:20` собирает фронтенд, `python:3.12-slim` с uv ставит бэкенд, итоговый образ slim без инструментов сборки. Публикуется в `ghcr.io/lom911/gantt-ai-planner` как публичный пакет с тегами `sha-<short>` и `latest`.
- **CI** (`ci.yml`, на PR и push):
  - ruff, format-check, mypy (strict для `domain/` и `excel/`);
  - pytest с Postgres в service container;
  - eslint, `tsc`, vitest, сборка фронтенда;
  - Playwright e2e с поддельным LLM на собранном образе;
  - gitleaks.
- **CD** (`deploy.yml`, на push в `main` после зелёного CI):
  - сборка и публикация образа;
  - Trivy (падает на CRITICAL);
  - `ssh deploy@host sha-<short>` через forced command;
  - проверка `https://…/healthz`.
- **Подготовка сервера.** Скрипт `deploy/bootstrap.sh` идемпотентен, запускается вручную один раз, каждый шаг согласуется с владельцем. Он создаёт:
  - пользователя `deploy`, sudoers, обёртку;
  - каталоги и секреты;
  - стек Caddy;
  - cron для бэкапа.
  До появления CD используется `scripts/deploy-manual.sh`.
- **Проверка при первом деплое:** порты 80/443 доступны из интернета.
