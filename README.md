# Gantt AI Planner

Веб-планировщик проекта: интерактивная диаграмма Ганта плюс чат с AI-агентом, который правит план на естественном языке через MCP. План можно загрузить из Excel и выгрузить обратно без потерь.

Стек: **React 19 + TypeScript** (Vite, Tailwind v4, shadcn/ui, TanStack Query, SVAR Gantt) и **Python/FastAPI** (SQLAlchemy 2 + PostgreSQL, MCP-сервер на FastMCP, агент на Anthropic SDK).

Тестовое задание: «Full-stack разработчик AI-native продукта (React + FastAPI)».

## Демо

**Онлайн-демо: https://gantt-ai-planner.duckdns.org** — задеплоено на VPS владельца (Docker Compose, Caddy + Let's Encrypt; образ собран из коммита `e159b83`) и проверено на настоящей LLM. Живой smoke-тест на проде (агент на модели через OpenRouter, `anthropic/claude-sonnet-5`) прошёл: массовый сдвиг задач одного исполнителя ровно на 3 рабочих дня, назначение исполнителя по неполному имени, добавление задачи с зависимостью и исполнителем одним ходом, переспрос при неоднозначной команде («какую из 4 подходящих задач?») и подтверждение перед массовым удалением (`confirmation_required` → переспрос → удаление после «да»). Подробности — в `docs/ai-usage.md`.

## Быстрый старт

### Вариант A — всё в Docker (полный стек)

```bash
docker compose --profile full up --build
```

Открыть http://localhost:8000. По умолчанию используется детерминированный fake-LLM (`LLM_PROVIDER=fake`) — работает без ключей и подходит для проверки функциональности; в тулбаре при этом показан бейдж «Демо-режим без LLM» (см. раздел «Задача: история, загрузка исполнителей, тема» ниже). Чтобы агент отвечал настоящей моделью Claude, есть два варианта провайдера (`backend/app/agent/llm.py`, `backend/app/config.py`):

```bash
# напрямую через Anthropic API
ANTHROPIC_API_KEY=sk-ant-... LLM_PROVIDER=anthropic docker compose --profile full up --build

# через OpenRouter (Anthropic-совместимый эндпоинт), модель anthropic/<LLM_MODEL>
OPENROUTER_API_KEY=sk-or-v1-... LLM_PROVIDER=openrouter docker compose --profile full up --build
```

Ключ вида `sk-or-...`, вставленный в `ANTHROPIC_API_KEY` при `LLM_PROVIDER=anthropic`, тоже распознаётся автоматически и уходит через OpenRouter (с одноразовым предупреждением в логе, без смены `LLM_PROVIDER`) — именно так задеплоено онлайн-демо: у владельца оказался ключ OpenRouter.

Профиль `full` собирает единый образ (multi-stage `Dockerfile`: сборка фронтенда → образ backend) и поднимает три сервиса из `docker-compose.yml`: `db`, разовый `migrate` (`alembic upgrade head`) и `app` (uvicorn, порт 8000). Проверено: `docker compose --profile full up --build -d --wait` поднимает стек, `GET /healthz` отвечает `{"status":"ok"}`.

### Вариант B — локальная разработка (backend и frontend отдельно)

1. Поднять только базу данных:

   ```bash
   docker compose up -d db
   ```

   Postgres 17 поднимется на `127.0.0.1:55432` (пользователь/БД `planner`, см. `docker-compose.yml` и `.env.example`).

2. Backend (Python 3.12, менеджер пакетов [uv](https://docs.astral.sh/uv/)):

   ```bash
   cd backend
   uv sync
   uv run alembic upgrade head
   uv run uvicorn app.main:create_app --factory --reload
   ```

   API поднимется на http://localhost:8000, интерактивная документация — на `/api/docs`. Backend читает настройки из `backend/.env` (скопируйте `.env.example` из корня репозитория) — там же переменная `LLM_PROVIDER=fake`, по умолчанию агент работает без ключа Anthropic.

3. Frontend (Node 26; не ниже 22.12 — этого требуют vitest 5 и jsdom 30; Vite):

   ```bash
   cd frontend
   npm ci
   npm run dev
   ```

   Откроется http://localhost:5173. Dev-сервер Vite проксирует `/api` и `/healthz` на `http://localhost:8000` (см. `frontend/vite.config.ts`), поэтому backend из пункта 2 должен быть запущен.

Переменные окружения перечислены в `.env.example` (корень репозитория) и разбираются `backend/app/config.py`: `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD`, `PUBLIC_ORIGIN`, `COOKIE_SECURE`, `LLM_PROVIDER` (`fake` | `anthropic` | `openrouter`), `LLM_MODEL`, `ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`.

Полный прогон можно направить на живой сервер (настоящая LLM; одна сессия, в конце её данные удаляются):

```bash
cd frontend && E2E_BASE_URL=https://gantt-ai-planner.duckdns.org npx playwright test -c e2e/playwright.config.ts e2e/full-ui.spec.ts
```

```
Browser (React SPA)
  ├─ REST  /api/*            ─┐
  ├─ SSE   /api/chat (stream) │
  └─ SSE   /api/events        │     Внешний MCP-клиент (Claude Code/Desktop)
                              ▼             │  Streamable HTTP + Bearer mcp_…
┌──────────────────────── FastAPI (1 uvicorn worker) ─────────────────────┐  │
│ api/        роутеры, сессии по cookie, проверка Origin,                 │  │
│             выпуск/отзыв MCP-токена (routes_mcp_token.py)               │  │
│ agent/      цикл агента (Anthropic SDK) ──► MCP-клиент внутри процесса ─┼┐ │
│ mcp_server/ FastMCP-сервер "planner" (инструменты), auth.py ◄───────────┼┴─┘
│             (Bearer-токен ──► session_id), смонтирован на /mcp          │
│ services/   PlanService: загрузить → применить операции → пересчитать → │
│             сохранить версию → отправить событие                        │
│ domain/     модели, планировщик (CPM), операции, валидация, diff (без I/O)│
│ excel/      парсер импорта, экспорт (без I/O)                           │
│ db/         модели SQLAlchemy 2, репозиторий                            │
│ migrations/ миграции Alembic                                            │
└───────────────────────────────────────────────────────────────────────┘
                              │ asyncpg
                        PostgreSQL 17
```

Внешний `/mcp` — тот же FastMCP-сервер `planner`, что использует агент внутри процесса, смонтирован по Streamable HTTP (`backend/app/main.py`, класс `McpOriginGate` — проверка Origin и обход 307-редиректа fastmcp на `/mcp` без слэша). Доступ — по Bearer-токену `mcp_...`, который выдаётся на сессию через диалог «Подключить MCP» (см. раздел MCP ниже). У агента внутри процесса и у внешнего клиента один и тот же набор инструментов и один и тот же `PlanService.apply` под капотом — разница только в транспорте.

Реальные пакеты кода: `backend/app/domain`, `backend/app/excel`, `backend/app/services`, `backend/app/mcp_server`, `backend/app/agent`, `backend/app/api`, `backend/app/db`, `backend/app/migrations`, `backend/app/main.py`.

## Ключевые решения (и почему)

- **Автопланирование по CPM, только связи «конец → начало» (FS + лаг).** Прямой и обратный проход по графу задач (топологическая сортировка Кана) считают ранние/поздние даты, резерв (`slack`) и критический путь при каждом чтении плана — план не хранит вычисленные даты, только исходные данные (длительности, зависимости, ограничение «не раньше»). Это гарантирует, что даты в интерфейсе всегда согласованы с последними правками, независимо от того, кто их внёс — человек, агент или Excel-импорт. Другие типы связей (SS/FF/SF) и отрицательный лаг сознательно не поддержаны на первой итерации — см. Roadmap.
- **JSONB-снимки версий плана + undo одним ходом агента.** Каждое успешное применение пакета операций сохраняет снимок входного состояния как новую версию с полем `source` (`user`/`agent`/`mcp`/`import`/...) и, для агента, общим `turn_id`. Отмена откатывает сразу всю группу версий одного хода агента, а не отдельные шаги внутри него — это то, что пользователь интуитивно ожидает от «отменить последнее». Плюс это проще, чем operational transform, и достаточно для плана до 500 задач.
- **`PlanService` — единственный путь изменения плана.** Правки из интерфейса (включая перетаскивание/растягивание на диаграмме), вызовы инструмента `apply_operations` из агента и из внешнего MCP-клиента идут через один и тот же метод `apply(session, ops, source)`. Так гарантируется одинаковая валидация, пересчёт расписания и генерация версии/diff/события независимо от источника правки.
- **MCP-сервер + два MCP-клиента.** Агент вызывает инструменты плана не напрямую, а через настоящий MCP-протокол (FastMCP) — сначала это был только клиент внутри процесса, теперь тот же сервер и контракт инструментов домонтирован по Streamable HTTP на `/mcp` для внешних клиентов (Claude Code/Desktop), без изменения самих инструментов.
- **Fake LLM для детерминированных тестов и демо.** `LLM_PROVIDER=fake` — реализация с фиксированными сценариями (ключевые фразы → заранее заданные вызовы инструментов), без сети и без ключа. Интеграционные тесты хода агента и Playwright e2e работают на ней, а не на реальной модели — так тесты воспроизводимы и не стоят денег.
- **SSE для стрима чата и живых обновлений плана.** `POST /api/chat` стримит ответ модели через `text/event-stream`; отдельный `GET /api/events` шлёт событие `plan_changed`, когда план меняется (в том числе из-за агента, правки на диаграмме или внешнего MCP), чтобы диаграмма обновлялась сама, без опроса. SSE выбран как более простой протокол, чем WebSocket, для однонаправленного потока «сервер → браузер».
- **Сессии по cookie, без обязательной регистрации.** Первый запрос без cookie создаёт сессию с демо-планом; токен сессии хранится на сервере только как `sha256`-хэш. Это соответствует задаче: приложение — публичное демо для одного пользователя за раз, полноценная авторизация и общие планы — в Roadmap.
- **SVAR React Gantt (MIT).** Выбрана после сравнения с DHTMLX и другими вариантами по лицензии, поддержке React 19 и возможностям бесплатной версии (подробности решения — в `docs/ai-usage.md`). Диаграмма — тонкий клиент над планом, вычисленным на backend: перетаскивание/растягивание бара и рисование связи только классифицируют действие пользователя и шлют одну операцию (`move_task`/`update_task`/`add_dependency`) на `POST /api/plan/operations` — пересчёт расписания всегда делает сервер, ни одна дата на клиенте не считается заново (`frontend/src/components/gantt/interactions.ts`). Клик по задаче открывает модалку редактирования вместо встроенного редактора SVAR.
- **PostgreSQL вместо SQLite.** План хранится целиком как JSONB-снимок (без отдельных таблиц задач — в плане до 500 задач это оправдано простотой), но версии, история чата и сессии — это конкурентный доступ из нескольких запросов и фоновой очистки одновременно, для чего нужна настоящая СУБД с транзакциями и ролями.

## Формат Excel

### Импорт

- `.xlsx`, до 2 МБ (`MAX_UPLOAD_MB` в настройках), читается первый лист.
- Строка заголовков — первая строка, где найдена колонка задачи. Сравнение без учёта регистра/пробелов, по синонимам (см. `backend/app/excel/headers.py`):
  - `№`: `№`, `#`, `id`, `номер`;
  - задача: `задача`, `название`, `наименование`, `task`, `name`;
  - описание: `описание`, `description`;
  - исполнитель: `исполнитель`, `ответственный`, `assignee`, `owner`, `resource`;
  - длительность: `длительность`, `дни`, `duration`, `days`;
  - предшественники: `предшественники`, `зависимости`, `predecessors`, `depends on`;
  - необязательная колонка **«Не раньше»**: `не раньше`, `начать не раньше`, `snet`, `start no earlier than` — даты в ней становятся ограничением `constraint_start`.
- Обязательны колонки «задача» и «длительность». Остальные — опциональны, неизвестные колонки игнорируются, пустые строки пропускаются.
- **Формат длительности:** `5`, `5д`, `5 д.`, `5 дн`, `5 дней`, `5d`, `1 нед`, `1w` (неделя = 5 рабочих дней). Дробное значение округляется вверх с предупреждением; пустое или `0` превращается в `1` с предупреждением.
- **Формат предшественников:** элементы разделяются `,` или `;`, у каждого — опциональный лаг вида `+N`, например `3+2`. Число — это `№` (если колонка `№` есть) или порядковый номер строки в файле; текст — название задачи (если название неоднозначно — ошибка «укажите №»).
- **Ошибки, блокирующие импорт:** нет обязательной колонки, пустое название, неизвестная/самозамкнутая ссылка, цикл в зависимостях, больше 500 задач, больше 2000 связей, лаг больше 365 дней, повторяющийся `№`. Все ошибки собираются в один отчёт с номерами строк.
- **Предупреждения** (дробная/нулевая длительность и т.п.) импорт не блокируют.
- При успехе план заменяется целиком, создаётся отменяемая версия (`source=import`), в чат добавляется системное сообщение об импорте.

### Экспорт

Лист «План» с колонками `№, Задача, Описание, Исполнитель, Длительность, Предшественники, Не раньше, Начало, Окончание, Резерв, Критическая`; предшественники — по `№` с лагом `+N`; даты — как даты Excel; заголовки жирные, первая строка закреплена. Имя файла: `plan-YYYY-MM-DD.xlsx`.

Экспортированный файл загружается обратно без потерь (номера задач и ограничение «Не раньше» сохраняются) — это проверяется тестом `backend/tests/unit/test_excel_export.py`. Колонка «Не раньше» в исходном ТЗ не описана, мы добавили её сами, чтобы ограничения переживали цикл экспорт → импорт.

**Пример файла:** `examples/sample-plan.xlsx` («Переезд офиса», 15 задач, смешанные форматы длительности и предшественников) — сгенерирован скриптом `scripts/make_sample_excel.py`.

## MCP

Инструменты MCP-сервера `planner` (`backend/app/mcp_server/server.py`): `get_plan()`, `find_tasks(query?, assignee?, critical_only?)`, `get_task(id)`, `get_resource_load(assignee?)`, `apply_operations(operations, confirmed?)` (до 200 операций в пакете), `undo()`. У инструментов нет параметра `session_id` — сессия определяется транспортом, поэтому ни модель, ни внешний клиент не может обратиться к чужому плану.

Два клиента одного и того же сервера:

- **Внутри процесса** — агент вызывает инструменты через `PlanToolClient` (`backend/app/mcp_server/client.py`) по in-memory транспорту fastmcp; сессия здесь берётся из contextvar хода агента.
- **Внешний, по HTTP** — сервер смонтирован на `/mcp` как Streamable HTTP (`backend/app/main.py`), с Bearer-аутентификацией (`backend/app/mcp_server/auth.py`, `SessionTokenVerifier`).

**Подключение стороннего клиента (Claude Code/Desktop):** кнопка «Подключить MCP» в тулбаре открывает диалог (`frontend/src/components/McpConnectDialog.tsx`), который по `POST /api/mcp-token` выпускает токен вида `mcp_...` на текущую сессию и показывает его один раз вместе с готовыми:
- командой для Claude Code — `claude mcp add --transport http planner <url> --header "Authorization: Bearer <token>"`;
- JSON-конфигом для Claude Desktop (`claude_desktop_config`).

Токен живёт один на сессию: повторный выпуск отзывает предыдущий (`backend/app/api/routes_mcp_token.py`); в БД хранится только `sha256`-хэш и короткий префикс, TTL — 7 дней (`TOKEN_TTL_DAYS`); кнопка «Отозвать» в том же диалоге вызывает `DELETE /api/mcp-token` немедленно.

**Ограничение принятое сознательно:** статический долгоживущий Bearer-токен вместо OAuth 2.1 — упрощение для одного пользователя на сессию, см. `docs/roadmap-to-production.md`.

## Диаграмма Ганта: интерактивность

Правки прямо на диаграмме идут тем же путём, что и правки из чата/MCP — через `POST /api/plan/operations` и единый `PlanService.apply` (`frontend/src/components/gantt/{GanttView.tsx,interactions.ts}`):

- **Перетаскивание бара** → `move_task`: новая дата начала становится ограничением «не раньше» (`constraint_start`) задачи.
- **Растягивание бара** → `update_task`: новая длительность в рабочих днях.
- **Рисование связи между барами** → `add_dependency` (только «конец → начало»; если библиотека сообщает другой тип связи, показывается тост об ошибке и связь не создаётся).
- **Блокировка на время хода агента.** Пока агент выполняет ход (`agentBusy`), диаграмма переводится в `readOnly` — перетаскивание/растягивание/рисование связей не начинаются, чтобы не конфликтовать с правками агента.
- **Ошибки — тостом, бар возвращается на место.** Если сервер отклонил операцию (валидация, конфликт), правка на клиенте не подтверждается: показывается toast с текстом ошибки, а бар/связь визуально откатываются к последнему подтверждённому состоянию плана (см. комментарий про `revision`/`snapBack` в `GanttView.tsx`).
- **Оптимистичная блокировка по версии.** Каждая правка из интерфейса (`POST /api/plan/operations`, `/undo`, `/redo`) несёт `expected_version` — версию плана, которую видит вкладка. Если план уже изменила другая вкладка, агент или MCP-клиент, сервер отвечает `409 version_conflict` (в `details` — текущая версия), правка не применяется, вкладка перезагружает план и показывает тост. Агент и MCP-клиент поле не передают: они действуют на только что прочитанное состояние под той же блокировкой сессии.

Дополнительно на диаграмме: **подсказка при наведении** на бар (даты, рабочие дни, исполнитель, резерв), **легенда** (критический путь / перегрузка / изменено — `GanttLegend.tsx`), **автопрокрутка к сегодняшнему дню** при открытии, и **компактный тулбар на мобильном** — узкие экраны показывают только иконки без подписей и укороченную сетку колонок (№ + Задача, 180 px), а справа от неё — прокручиваемый таймлайн; переключение вкладок «Диаграмма»/«Чат» не прерывает идущий ход агента.

## Задача: история, загрузка исполнителей, тема

- **История изменений задачи.** Модалка задачи показывает историю правок конкретной задачи (`GET /api/plan/tasks/{id}/history`, компонент `frontend/src/components/task/TaskHistory.tsx`).
- **Панель загрузки исполнителей** («Загрузка», `frontend/src/components/ResourcePanel.tsx`) — сколько рабочих дней занято у каждого исполнителя и где перегрузка; считается на клиенте из уже загруженного плана (`computeResourceSummary`, `frontend/src/lib/resourceSummary.ts`), отдельного запроса нет. Агенту и внешним MCP-клиентам загрузку отдаёт отдельный инструмент `get_resource_load` (задачи исполнителя по датам и пары пересекающихся задач).
- **Переключатель темы** — светлая/тёмная/как в системе (`frontend/src/hooks/useTheme.ts`, переключается из тулбара).
- **Демо-режим без LLM.** `GET /api/meta` отдаёт `llm_mode`; если ключ Anthropic не задан (`LLM_PROVIDER=fake` или пустой ключ), в тулбаре показывается бейдж «Демо-режим без LLM» (`backend/app/api/routes_meta.py`, `frontend/src/components/Toolbar.tsx`).

## Примеры команд для чата

Подсказки, которые видит пользователь в пустом чате (`frontend/src/components/chat/ChatPanel.tsx`):

- «Сдвинь все задачи Дмитрия на 3 дня»
- «Перенеси задачу 6 на 2 дня»
- «Назначь задачу 19 на Игоря Петрова»
- «Добавь задачу «Ревью безопасности» на 2 дня после 10»

Агент переспрашивает, если по названию подходит несколько задач, и требует подтверждения, если один ход удаляет больше 5 задач или больше 50% плана.

## Ограничения

- **Один воркер uvicorn.** Шина событий (SSE) и блокировка сессии на время хода агента живут в памяти процесса — при нескольких воркерах или горизонтальном масштабировании события и блокировки не будут общими. Путь дальше — `LISTEN/NOTIFY` в Postgres (см. Roadmap).
- **Без праздников.** Календарь — только рабочие дни понедельник–пятница; официальные праздники не учитываются.
- **Только связи «конец → начало» (FS).** SS/FF/SF и отрицательный лаг не поддержаны.
- **Один исполнитель на задачу.** Мультиисполнители не поддержаны; «перегрузка» считается по пересечению дат у задач одного и того же исполнителя.
- **Нет вех** (задач нулевой длительности) — не отдельный тип задачи ни в модели, ни в Excel-формате.
- **Внешний MCP без OAuth 2.1.** Доступ — по статическому Bearer-токену на сессию (см. раздел MCP), а не по полноценному authorization code + PKCE.

Полный перечень технического долга и порядок его закрытия — в `docs/roadmap-to-production.md`.

## Безопасность и данные

- **Секреты.** Пароль БД и ключ Anthropic задаются файлами через Compose `secrets:` (`SECRETS_DIR`, см. `backend/app/config.py`) — в коде хранятся как `pydantic.SecretStr`, не попадают в логи. Локально — `.env` (в `.gitignore`), пример — `.env.example`.
- **Роли Postgres** (для прод-развёртывания, см. `deploy/initdb/10-roles.sh` и `deploy/compose.prod.yml`): `postgres` — только инициализация; `planner_owner` — владелец схемы, от него выполняются миграции; `planner_app` — только `SELECT/INSERT/UPDATE/DELETE`, с лимитом соединений и таймаутами.
- **Хранение сессий: TTL 14 дней.** Фоновая задача (`backend/app/services/cleanup.py`, запускается из `app/main.py`) раз в час удаляет сессии, у которых `last_seen_at` старше `SESSION_TTL_DAYS` (по умолчанию 14), и вызывает `forget()` на in-memory блокировках/шине событий, чтобы удалённые сессии не оставляли висящих записей в памяти процесса.
- **«Удалить мои данные».** `DELETE /api/session` каскадно удаляет сессию (версии плана, историю чата, токены MCP) и сбрасывает cookie.
- **Privacy-safe access log.** Каждый запрос логируется одной строкой — метод, путь, статус, длительность, префикс `session_id`; без query-строки, тела, cookie и заголовков (`backend/app/logging_setup.py`, собственный access-лог uvicorn отключён).
- **Атомарный рейт-лимит чата.** Проверка лимита и вставка сообщения идут в одной транзакции под `pg_advisory_xact_lock`, иначе конкурентные запросы могли бы обойти лимит гонкой (`backend/app/api/routes_chat.py`).
- **Лимиты на IP.** Не больше 20 новых сессий, 60 сообщений чата, 1200 правок плана и 60 загрузок Excel в час с одного адреса (`SESSION_LIMIT_PER_IP_HOUR`, `CHAT_LIMIT_PER_IP_HOUR`, `MUTATION_LIMIT_PER_IP_HOUR`, `IMPORT_LIMIT_PER_IP_HOUR`; скользящее окно в памяти процесса, `backend/app/services/iplimit.py`) — чтобы один клиент не раздувал БД снимками плана и не выбирал общий дневной лимит чата. IPv6-клиенты считаются по подсети /64. Дневной лимит чата на всё приложение ведётся в отдельной таблице `chat_usage`, не связанной с сессиями, — удаление сессии его не обнуляет. Адрес клиента берётся из последнего звена `X-Forwarded-For` только при `TRUST_PROXY=true` (прод, где запросы приходят только через Caddy), иначе — адрес TCP-соединения. Пакет операций — не больше 200 штук (`MAX_BATCH_OPS`).
- **Защита импорта Excel.** Лимит на количество строк и проверка заявленного (несжатого) размера содержимого архива `.xlsx` против «zip-бомбы» — до распаковки (`backend/app/excel/parse.py`); имя загружаемого файла санитизируется перед использованием (`backend/app/api/routes_plan.py`, `sanitize_filename`).
- **CI/CD.** Деплой только из `main` этого репозитория: GitHub Environment `production` (`.github/workflows/deploy.yml`) разрешает запуск только из ветки `main` (ручное подтверждение через required reviewers не включено — деплой идёт автоматически после зелёного CI) и хранит секреты `DEPLOY_SSH_KEY`/`DEPLOY_KNOWN_HOSTS` и переменные `DEPLOY_HOST`/`DEPLOY_USER`; образ сканируется Trivy перед публикацией в GHCR. CD настроен и запускается после каждого мержа в `main` (по завершении CI): по SSH деплой-ключом передаётся новый тег, а сам ключ на сервере ограничен forced-командой `planner-deploy-wrapper`, которая принимает только один аргумент вида `sha-<hex>` (детали — `docs/runbook.md`, §2). Приложение уже задеплоено на VPS по этому рантбуку: первый релиз выполнен вручную (§1 — `bootstrap.sh`, первый `docker compose up`, проверка `/healthz`), дальнейшие обновления идут через CD — первый автоматический деплой после мержа PR #1 в `main` прошёл (образ `ghcr.io/alomaev-hue/gantt-ai-planner:sha-ca97d60` собран, просканирован Trivy, опубликован и скачан сервером без логина: пакет привязан к публичному репозиторию и унаследовал публичную видимость). Эксплуатация — там же: первичная настройка VPS, деплой, откат, ротация секретов; его ручные команды заменяют `scripts/deploy-manual.sh` из спецификации (§14), отдельного скрипта нет; Dependabot обновляет зависимости backend (uv), frontend (npm), GitHub Actions, `Dockerfile` и compose-файлы деплоя (`.github/dependabot.yml`).
- **Данные уходят к Anthropic.** Сообщения чата и компактное представление плана отправляются в API Anthropic для генерации ответа и вызова инструментов. **Используйте только вымышленные данные** — не загружайте реальные ФИО, контакты или иные персональные данные в демо-план или Excel-файлы. Обработка и хранение реальных персональных данных граждан РФ по 152-ФЗ (в том числе требование о хранении/обработке на территории РФ) для сервиса, физически размещённого не в РФ и использующего внешний LLM-API, не проработана и записана как риск и пункт Roadmap.

## Как использовались AI-ассистенты

Кратко (полный журнал по датам и конкретным решениям — в `docs/ai-usage.md`):

Проектирование и реализация выполнены **Claude Code** (оркестрация, субагенты) с **Codex** в роли второго мнения. Процесс:

1. **Опрос по дизайну** (skill `grilling`, 5 раундов) — по каждому вопросу Claude предлагал вариант, решение принимал человек; человек изменил три рекомендации (свой VPS вместо Render, PostgreSQL вместо SQLite, домен DuckDNS).
2. **Фоновые исследования** отдельными субагентами: сравнение React-библиотек Ганта (выбрана SVAR, MIT), соглашения по VPS/Caddy/DuckDNS из соседних проектов пользователя, практики хранения секретов и данных под 152-ФЗ.
3. **Спецификация**, которую написал Claude и при самопроверке нашёл в ней противоречие (колонка «Не раньше» нужна, чтобы экспорт грузился обратно без потерь).
4. **Второе мнение Codex** по всему дизайну — часть замечаний принята (сокращение объёма по фазам, упрощение истории изменений, перенос внешнего MCP во вторую фазу), часть отклонена с объяснением почему (например, «чат без MCP» — тогда MCP стал бы декоративным).
5. **План** из 23 задач, для каждой — файлы, интерфейсы, тесты, эталонный код; неочевидные факты об API библиотек (fastmcp, anthropic SDK, sse-starlette) субагент сначала проверял пробными запросами в отдельном venv.
6. **Subagent-driven development с ревью на каждой задаче:** отдельный субагент реализует задачу по TDD (красный тест → код → зелёный тест), отдельный субагент-ревьюер проверяет соответствие плану и качество. Конкретные случаи, где ревью поймало ошибку AI: исполнитель на дешёвой модели добавил в демо-план 3 лишние задачи, чтобы пройти тест (это сломало бы контракт для последующих задач) — ревьюер это заметил и вернул задачи к исходному состоянию; ревьюер также нашёл ошибку на единицу в подсчёте переводов строк в самом плане.

Подробности, включая разногласие по строке атрибуции коммитов, — в `docs/ai-usage.md`.
